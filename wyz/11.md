# mxfp8_golden 三个 Python 文件小白解析

这份文档解析 `D:\test\ops-transformer\wyz_golden` 下的三个脚本：

- `run_mxfp8_cases.py`：用例入口，负责列 case，然后逐个调用主流程。
- `mxfp8_golden.py`：主逻辑，负责造输入、CPU golden 计算、NPU 调用、触发对比。
- `result_compare_method.py`：精度对比工具，负责把 CPU 结果和 NPU 结果逐元素比较并打印结论。

一句话总结：这三个文件是在验证一个 MXFP8 Flash Attention 算子的精度。脚本先在 CPU 侧用 PyTorch 手写一份“理论正确答案”，再调用 `torch_npu.npu_fused_infer_attention_score_v2` 跑 NPU 算子，最后把两边输出拉平后逐元素比较。

## 1. 怎么调用

在有 NPU、`torch_npu`、`torchair` 环境的机器上，进入目录后执行：

```bash
cd D:\test\ops-transformer\wyz_golden
python run_mxfp8_cases.py
```

调用链是：

```text
run_mxfp8_cases.py
  -> main()
    -> 遍历 CASES
      -> run_mxfp8_case(case=..., run_npu=True, catch_npu_error=True)
        -> generate_data()
        -> cpu_mxfp8_golden()
        -> npu_mxfp8_fa()
          -> mxfp8_fa_torch_npu()
            -> torch_npu.npu_fused_infer_attention_score_v2()
        -> result_compare_method.check_result()
```

当前真正打开的 case 只有一个，其他 case 都被注释掉了：

```python
{
    "name": "b_1_s1_1_s2_256_PA_sparse3_n1_1_n2_1_rope",
    "B": 1,
    "Nq": 1,
    "Nkv": 1,
    "Sq": 1,
    "Skv": 256,
    "D": 128,
    "enable_rope": False,
    "D_rope": 64,
    "scale": 0.08838834764831843,
    "layout": "TND",
    "enable_pa": True,
    "kv_cache_layout": "BnNBsD",
    "block_size": 512,
    "sparse_mode": 3,
}
```

这些字段的含义：

| 字段 | 含义 |
|---|---|
| `B` | batch 数，当前是 1 |
| `Nq` | Query 头数，当前是 1 |
| `Nkv` | Key/Value 头数，当前是 1 |
| `Sq` | Query 序列长度，当前是 1 |
| `Skv` | Key/Value 序列长度，当前是 256 |
| `D` | 每个 head 的维度，当前是 128 |
| `enable_pa` | 是否走 PagedAttention KV cache，当前打开 |
| `kv_cache_layout` | PA 缓存布局，当前是 `BnNBsD` |
| `sparse_mode` | mask 模式，当前是 3 |
| `enable_rope` | 是否额外传入 rope 部分，当前关闭 |

## 2. 三个文件各自做什么

### 2.1 run_mxfp8_cases.py

这个文件很短，只有两件事：

1. 从 `mxfp8_golden.py` 导入 `run_mxfp8_case`。
2. 定义 `CASES` 列表，然后在 `main()` 里逐个跑。

核心代码可以理解成：

```python
for case in CASES:
    run_mxfp8_case(case=case, run_npu=True, catch_npu_error=True)
```

注意：这里的 `passed_count`、`total_count`、`status` 相关代码都被注释了，所以当前脚本不会汇总打印“总共几个 pass”。真正的对比结果来自 `result_compare_method.check_result()` 打出来的日志。

### 2.2 mxfp8_golden.py

这是主文件，里面分成几大块：

| 区域 | 作用 |
|---|---|
| 全局配置 | 默认 B、N、D、PA、layout、seed、FP8 类型等 |
| scale 计算 | 计算 MXFP8 量化和反量化 scale |
| layout 转换 | BNSD、TND、PA cache 等格式互转 |
| `generate_data()` | 构造 Q/K/V 输入，并转成 FP8 |
| `cpu_mxfp8_golden()` | CPU 侧模拟 Flash Attention |
| `npu_mxfp8_fa()` | 整理 NPU 入参 |
| `mxfp8_fa_torch_npu()` | 真正调用 torch_npu 算子 |
| `run_mxfp8_case()` | 把一整个 case 串起来 |

### 2.3 result_compare_method.py

这个文件是对比工具，核心函数是：

```python
check_result(expect, npu_result)
```

其中：

- `expect`：CPU golden 输出，也就是理论正确答案。
- `npu_result`：NPU 算子输出。

它会把两边都拉平成一维，然后逐元素比较。

## 3. 主流程从头到尾怎么跑

入口在 `run_mxfp8_case()`，它按四步执行：

```text
Step 1: 数据生成
Step 2: CPU Golden
Step 3: NPU 调用
Step 4: Atten OUT 精度对比
```

### Step 0：把 case 写到全局变量

`run_mxfp8_case(case=...)` 一开始会把 case 里的配置写到 `mxfp8_golden.py` 的全局变量里，例如：

```python
B = int(case["B"])
N_q = int(case["Nq"])
N_kv = int(case["Nkv"])
D = int(case["D"])
ACTUAL_SEQ_Q = [int(case["Sq"])] * B
ACTUAL_SEQ_KV = [int(case["Skv"])] * B
INPUT_LAYOUT = case.get("layout", "TND")
SPARSE_MODE = int(case.get("sparse_mode", 0))
ENABLE_PA = bool(case.get("enable_pa"))
ENABLE_ROPE = bool(case.get("enable_rope", False))
```

当前 case 写进去以后，关键配置就是：

```text
B = 1
N_q = 1
N_kv = 1
D = 128
ACTUAL_SEQ_Q = [1]
ACTUAL_SEQ_KV = [256]
INPUT_LAYOUT = TND
ENABLE_PA = True
KV_CACHE_LAYOUT = BnNBsD
SPARSE_MODE = 3
ENABLE_ROPE = False
```

有两个限制也在这里检查：

- `N_q % N_kv == 0`，因为 GQA 要求 Q 头数能整除 KV 头数。
- `INPUT_LAYOUT == "TND"`，这个脚本当前只允许 TND 输入。

## 4. Step 1：如何构造输入 case

输入构造发生在 `generate_data()`。

### 4.1 先确定真实序列长度

```python
actual_seq_q = normalize_seq_lens(ACTUAL_SEQ_Q, B)
actual_seq_kv = normalize_seq_lens(ACTUAL_SEQ_KV, B)
max_sq = max(actual_seq_q)
max_skv = max(actual_seq_kv)
```

当前 case：

```text
actual_seq_q = [1]
actual_seq_kv = [256]
max_sq = 1
max_skv = 256
```

### 4.2 生成 FP16 的 Q/K/V

脚本用固定随机种子生成输入，这样每次跑出来的数据一样，方便复现。

```python
torch.manual_seed(SEED_Q)
q_fp16 = torch.zeros(B, N_q, max_sq, D, dtype=torch.float16)
q_fp16.uniform_(-5.0, 5.0)

torch.manual_seed(SEED_K)
k_fp16 = torch.zeros(B, N_kv, max_skv, D, dtype=torch.float16)
k_fp16.uniform_(-5.0, 5.0)

torch.manual_seed(SEED_V)
v_fp16 = torch.zeros(B, N_kv, max_skv, D, dtype=torch.float16)
v_fp16.uniform_(-5.0, 5.0)
```

当前 case 的形状是：

```text
q_fp16: [1, 1, 1, 128]
k_fp16: [1, 1, 256, 128]
v_fp16: [1, 1, 256, 128]
```

这里的默认内存布局叫 BNSD：

```text
B = batch
N = head 数
S = sequence 长度
D = head 维度
```

所以 `[1, 1, 256, 128]` 就是：1 个 batch，1 个 KV head，256 个 token，每个 token 128 维。

### 4.3 如果打开 rope，会额外生成 qr/kr

如果 `ENABLE_ROPE=True` 且 `D_rope > 0`，还会生成：

```python
qr_bf16 = [B, N_q, max_sq, D_rope]
kr_bf16 = [B, N_kv, max_skv, D_rope]
```

当前 case 里 `enable_rope=False`，所以：

```text
qr_bf16 = None
kr_bf16 = None
```

### 4.4 计算 MXFP8 scale

这个脚本不是直接把 FP16 转 FP8，而是先按 group 算 scale。

#### Q/K 的 scale：按 token 分组

Q/K 使用 `get_mxfp8_per_token_group_quant_scale()`。

它沿着最后一维 D 分组，每 32 个元素一组：

```text
D = 128
group_size = 32
所以每个 token 有 128 / 32 = 4 个 scale
```

当前形状：

```text
quant_scale_q: [1, 1, 1, 4]
quant_scale_k: [1, 1, 256, 4]
```

每组 scale 的计算逻辑是：

```text
1. 找这一组里面绝对值最大的数 max_abs
2. 取 floor(log2(max_abs))
3. 减去 FP8 E4M3 的最大指数 emax_elem=8
4. 得到 shared_exp
5. scale = 2 ** shared_exp
```

如果一整组全是 0，就把 scale 设成 1。

#### V 的 scale：按 channel 分组

V 使用 `get_mxfp8_per_channel_group_quant_scale()`。

它不是沿 D 分组，而是沿 S 分组，也就是每 32 个 token 一组：

```text
Skv = 256
group_size = 32
所以 V 的 S 方向有 256 / 32 = 8 个 scale group
```

当前形状：

```text
quant_scale_v: [1, 1, 8, 128]
```

意思是：每 32 个 token 共用一套 scale，但每个 D channel 都有自己的 scale。

### 4.5 反量化 scale

算出量化 scale 后，脚本又算反量化 scale：

```python
dequant_scale_q = 1 / quant_scale_q
dequant_scale_k = 1 / quant_scale_k
dequant_scale_v = 1 / quant_scale_v
```

这几个 `dequant_scale_*` 后面会同时给 CPU golden 和 NPU 算子使用。

### 4.6 转成 FP8 输入

Q/K：

```python
q_fp8 = (q_fp16 * quant_scale_q 展开到 D 维).to(torch.float8_e4m3fn)
k_fp8 = (k_fp16 * quant_scale_k 展开到 D 维).to(torch.float8_e4m3fn)
```

V：

```python
v_fp8 = (v_fp16 * quant_scale_v 展开到 S 维).to(torch.float8_e4m3fn)
```

当前最终输入形状仍然是：

```text
q_fp8: [1, 1, 1, 128]
k_fp8: [1, 1, 256, 128]
v_fp8: [1, 1, 256, 128]
```

只是 dtype 变成了 `torch.float8_e4m3fn`。

### 4.7 如果打开 PA，生成 block_table

当前 `ENABLE_PA=True`，所以会生成 `block_table_torch`。

逻辑是：

```python
block_num = sum(ceil(seq_kv / BLOCK_SIZE))
max_blocks = max(ceil(seq_kv / BLOCK_SIZE))
block_idx_list = torch.randperm(block_num)
block_table_torch = [B, max_blocks]
```

当前：

```text
Skv = 256
BLOCK_SIZE = 512
block_num = ceil(256 / 512) = 1
block_table_torch: [1, 1]
```

PA 的意思可以先粗略理解成：K/V 不再直接按普通连续序列传给 NPU，而是先放进一个“分页缓存”。`block_table` 告诉 NPU：某个 batch 的第几个逻辑块，实际存在哪个物理 block 里。

## 5. Step 2：CPU golden 怎么模拟计算

CPU 参考实现发生在 `cpu_mxfp8_golden()`。

它的目标是手写一份 Flash Attention 的计算过程，作为“正确答案”。

### 5.1 先把 FP8 转 FP32

```python
q_tensor = q_fp8.to(torch.float32)
k_tensor = k_fp8.to(torch.float32)
v_tensor = v_fp8.to(torch.float32)
```

注意：这里刚转成 FP32 时，还不是原始 FP16 的数值。因为 FP8 是量化后的值，还需要乘反量化 scale 才接近原始值。

### 5.2 如果是 GQA，广播 K/V

如果 `N_q != N_kv`，说明 Q 头数比 KV 头数多，要把 K/V 按比例复制给多个 Q head 使用。

当前 case：

```text
N_q = 1
N_kv = 1
```

所以不需要广播。

### 5.3 构造 mask

CPU 会构造两类 mask：

```text
q_padding_mask：挡住超过真实 Q 长度的位置
k_padding_mask：挡住超过真实 KV 长度的位置
```

如果 `SPARSE_MODE == 3`，还会构造 causal mask：

```python
delta = k_lens_acl - q_lens_acl
causal_mask = k_range > (q_range + delta)
mask_global = causal_mask | q_padding_mask | k_padding_mask
```

当前 case：

```text
q_len = 1
kv_len = 256
delta = 255
q_index = 0
k_index > 0 + 255 才会被 mask
```

而 K 的合法下标是 0 到 255，所以当前这个 case 基本不会因为 causal mask 挡掉有效 K，只会挡 padding。

### 5.4 按块模拟算子流水

CPU golden 没有一次性算完整矩阵，而是按块模拟硬件算子的流水。

```python
Q_BLOCK_SIZE = 128
K_BLOCK_SIZE = 128
V_BLOCK_SIZE = 256
```

当前 case：

```text
Sq = 1
Skv = 256

Q tiles = ceil(1 / 128) = 1
K tiles = ceil(256 / 128) = 2
V tiles = ceil(256 / 256) = 1
```

也就是说：

```text
Q 只有 1 块
K 有 2 块：K0 是 0..127，K1 是 128..255
V 有 1 块：V0 是 0..255
```

这就是代码里为什么有：

```python
for j in range(0, TILES_KV, 2):
    # 一次处理 K[j] 和 K[j+1]
    Vj = V_BLOCKS[j // 2]
```

它每次拿两块 K，对应一块 V。

### 5.5 QK 矩阵乘：算 attention 分数

第一块 K 的分数：

```python
S_ij = torch.matmul(
    Qi * deq_scale_q_i,
    (Kj * deq_scale_k_j).permute(0, 1, 3, 2)
)
```

白话版：

```text
1. Q 是 FP8 存的，先乘 dequant_scale_q 还原到近似真实值
2. K 是 FP8 存的，先乘 dequant_scale_k 还原到近似真实值
3. 做 Q x K^T，得到注意力分数
```

如果打开 rope，还会额外加一项：

```python
S_ij += torch.matmul(Q_rope, K_rope^T)
```

当前没有 rope，所以跳过。

然后做标准缩放：

```python
S_ij = S_ij / sqrt(D + D_rope)
```

当前就是：

```text
S_ij / sqrt(128)
```

之后把 mask 的位置填成负无穷：

```python
S_ij = S_ij.masked_fill(mask, -inf)
```

### 5.6 Online softmax：边扫 K 边维护 max 和 sum

普通 softmax 是：

```text
P = exp(S) / sum(exp(S))
O = P x V
```

但是 Flash Attention 不能一次性存完整的 S 和 P，所以会分块处理。分块处理时，为了数值稳定，需要维护三个东西：

| 变量 | 含义 |
|---|---|
| `mi` | 当前已经处理过的 K 块里的最大分数 |
| `si` | 当前 softmax 的分母累积，也就是 sum(exp(...)) |
| `oi` | 当前输出分子的累积，也就是 sum(P未归一化 x V) |

代码里一开始：

```python
out = zeros
o_sum = zeros
o_max = float最小值
```

每处理一个 K block，就更新这些累积量。

### 5.7 第一块 K 的概率

```python
m_block_j = max(S_ij)
m_block_j = m_block_j - log(p_scale)
m_block_j = max(mi, m_block_j)
P_ij_raw = exp(S_ij - m_block_j)
s_block_j = sum(P_ij_raw)
P_ij_drop = P_ij_raw.to(FP8).to(FP32)
```

这里最重要的是最后一行：CPU golden 特意把 softmax 概率 `P_ij_raw` 转成 FP8 再转回 FP32。

这不是多此一举，而是在模拟 NPU 算子内部的低精度行为。也就是说，CPU golden 不是数学上无限精确的 attention，而是尽量贴近 NPU 算子内部流水和量化路径的 golden。

### 5.8 第二块 K 的概率

如果 `j + 1 < TILES_KV`，说明还有第二块 K。当前 case 有两块 K，所以会进入这个分支。

它会同样计算：

```python
S_ij1
m_block_j1
P_ij1_raw
s_block_j1
P_ij1_drop
```

然后合并两块 K 的结果。

### 5.9 用 V 计算输出分子

当前两块 K 对应一块 V：

```python
Vj = V_BLOCKS[j // 2]
```

先反量化 V：

```python
Vj_dequant = Vj * deq_scale_v_j
```

再拆成两段：

```python
V_part1 = Vj_dequant[:, :, :Kj.shape[2], :]
V_part2 = Vj_dequant[:, :, Kj.shape[2]:Kj.shape[2] + Kj1.shape[2], :]
```

当前：

```text
V_part1 对应 K0，长度 128
V_part2 对应 K1，长度 128
```

然后：

```python
P_ij_Vj = P_ij_drop @ V_part1 + P_ij1_drop @ V_part2
```

### 5.10 更新 online softmax 的累积量

核心更新是：

```python
update_mul_j = exp(m_block_j - m_block_j1)
update_mul_si = exp(mi - m_block_j1)

si_new = update_mul_si * si + s_block_j * update_mul_j + s_block_j1
o_new = update_mul_si * oi + P_ij_Vj
```

白话解释：

```text
新 max 可能比老 max 大，所以老的 sum 和老的 output 都要按指数比例缩放一下，
这样所有分块结果才能放在同一个 softmax 分母体系里。
```

最后更新：

```python
s_BLOCKS[i] = si_new
m_BLOCKS[i] = m_block_j1
o_BLOCKS[i] = o_new
```

### 5.11 最终归一化

所有 K 块处理完后：

```python
out = out / (out_sum + EPSILON)
lse = o_max + log(out_sum + EPSILON)
```

最终返回：

```python
return out, lse
```

其中：

- `out` 是 attention 输出，形状仍是 BNSD。
- `lse` 是 log-sum-exp，如果 `ENABLE_LSE=True` 才会参与最终对比。

当前默认 `ENABLE_LSE=False`，所以只比 `out`。

## 6. Step 3：NPU 是怎么调用起来的

NPU 调用从 `npu_mxfp8_fa()` 开始。

### 6.1 设置 NPU 设备

```python
torch_npu.npu.set_device(int(DEVICE_ID))
```

默认：

```text
DEVICE_ID = 0
```

### 6.2 计算 softmax_scale

```python
softmax_scale = 1.0 / sqrt(D + D_rope)
```

当前：

```text
softmax_scale = 1 / sqrt(128)
```

这个和 CPU golden 里的 `S_ij / sqrt(d_total)` 对应。

### 6.3 确定 Q scale layout

```python
q_runtime_layout, q_group, q_s1, q_gs1 = resolve_q_scale_layout(actual_seq_q)
```

规则是：

```text
G = N_q / N_kv
S1 = max(actual_seq_q)
如果 G * S1 > 80，用 TND
否则用 N2TGD
```

当前：

```text
G = 1 / 1 = 1
S1 = 1
G * S1 = 1
所以 Q scale layout = N2TGD
```

### 6.4 Q 转成 NPU 需要的 layout

如果走 PA：

```python
npu_input_layout = "TND"
```

当前 `ENABLE_PA=True`，所以 Q 会从 BNSD 转成 TND：

```text
q_fp8: [1, 1, 1, 128]
q_npu: [1, 1, 128]
```

TND 可以理解成把 batch 和 sequence 压平成一个总 token 维：

```text
T = sum(actual_seq_q)
N = head
D = head 维度
```

### 6.5 scale 转成 e8m0fnu

NPU 侧的 dequant scale dtype 是：

```python
torch_npu.float8_e8m0fnu
```

CPU 里原本的 `dequant_scale_q/k/v` 是 FP32。脚本会用：

```python
fp32_to_e8m0fnu_safe()
```

把 FP32 scale 转成 uint8 形式的 e8m0 指数字节。

转换前会先做保护：

- 如果 scale 是 NaN/Inf，替换成最小正数。
- 如果 scale 是 0，也替换成最小正数。
- 如果转完出现 `0xFF`，直接报错，因为这在 NPU 侧可能变成 NaN。

### 6.6 PA 模式下 K/V 怎么准备

当前是 PA 模式，所以 K/V 不直接转 TND，而是先进 `mxfp8_pa_preprocessing()`。

#### FP8 K/V 数据

普通 K/V 从：

```text
[B, N, S, D]
```

变成：

```text
[BlockNum, N, BlockSize, D]
```

当前：

```text
K/V 原始: [1, 1, 256, 128]
BlockSize = 512
BlockNum = 1
K/V PA: [1, 1, 512, 128]
```

前 256 个位置是真实数据，后 256 个位置是 padding。

当前 `kv_cache_layout = "BnNBsD"`，所以输出就是 `[BlockNum, N, BlockSize, D]`，不做额外转置。

#### K scale

K scale 原始：

```text
dequant_scale_k: [1, 1, 256, 4]
```

因为 scale 最后一维是 4，需要 pack 成 `(Dg//2, 2)`：

```text
K scale PA: [1, 1, 512, 2, 2]
```

#### V scale

V scale 原始：

```text
dequant_scale_v: [1, 1, 8, 128]
```

V scale 会按两个 sequence group 交错 pack：

```text
V scale PA: [1, 1, 8, 128, 2]
```

这里 `8` 是 PA scale 的 pack block size，不是原始有效 group 数。真实有效 group 是 `ceil(256 / 32) = 8`，打包后逻辑上每两个 group 放在最后一维的 `2` 里面。

### 6.7 block_table 传给 NPU

```python
block_table_npu = block_table_torch.npu()
```

当前 block table 形状：

```text
[1, 1]
```

它告诉 NPU：batch 0 的第 0 个 KV block 实际放在哪个物理 block。

### 6.8 mask 传给 NPU

如果 `SPARSE_MODE == 0`：

```python
mask_arg = None
```

否则：

```python
mask_arg = torch.triu(torch.ones(2048, 2048, dtype=torch.bool), diagonal=1).npu()
```

当前 `SPARSE_MODE=3`，所以会传一个上三角 mask。

### 6.9 真正的 NPU 算子

真正调用在 `mxfp8_fa_torch_npu()` 里。

如果：

```python
GRAPH_PATH = 0
```

就走单算子直调：

```python
torch_npu.npu_fused_infer_attention_score_v2(...)
```

关键参数包括：

```python
query_quant_mode=6
key_quant_mode=6
value_quant_mode=8
query_dtype=torch.float8_e4m3fn
key_dtype=torch.float8_e4m3fn
value_dtype=torch.float8_e4m3fn
dequant_scale_query_dtype=torch_npu.float8_e8m0fnu
dequant_scale_key_dtype=torch_npu.float8_e8m0fnu
dequant_scale_value_dtype=torch_npu.float8_e8m0fnu
quant_scale_p=p_scale
out_dtype=torch.float16
```

这些要和 CPU golden 的模拟对应：

| NPU 参数 | CPU golden 对应逻辑 |
|---|---|
| Q/K FP8 + quant_mode 6 | Q/K per-token-group MXFP8 |
| V FP8 + quant_mode 8 | V per-channel-group MXFP8 |
| dequant scale e8m0fnu | CPU 里用 FP32 dequant scale 乘回去 |
| softmax_scale | CPU 里 `S / sqrt(D)` |
| sparse_mode + mask | CPU 里 `mask_global` |
| block_table + block_size | CPU 不需要真实 PA cache，但 NPU 需要 |

如果 `GRAPH_PATH` 不是 0，还支持 torch.compile 图模式：

| GRAPH_PATH | 含义 |
|---|---|
| 0 | 单算子直调 |
| 3 | 静态图 |
| 5 | 动态图 |
| 6 | tiling 下沉 |
| 7 | aclgraph |

当前默认是 0。

## 7. Step 4：最后怎么对比精度

对比发生在：

```python
cpu_tnd_torch = convert_q_bnsd_to_layout(cpu_out, ACTUAL_SEQ_Q, "TND")
result_compare_method.check_result(cpu_tnd_torch, atten_out)
```

为什么要转 TND？

因为 CPU golden 输出是 BNSD：

```text
[B, N, Sq, D]
```

而 NPU 在 PA 模式下输出是 TND：

```text
[T, N, D]
```

所以要先把 CPU 输出也转成 TND，再对比。

当前：

```text
CPU out BNSD: [1, 1, 1, 128]
CPU out TND: [1, 1, 128]
NPU out:     [1, 1, 128]
```

### 7.1 check_result 的比较逻辑

`check_result()` 先把两边拉平：

```python
real_data = npu_result.detach().cpu().flatten()
expect_data = cpu_result.detach().cpu().flatten()
```

当前总元素数：

```text
1 * 1 * 128 = 128
```

然后检查形状是否一致。如果元素个数不同，直接 Failed。

### 7.2 基础阈值

默认阈值：

```python
rtol = 0.005
atol = 0.000025
pct_thd = 0.005
max_diff_hd = 10
```

如果 NPU 输出 dtype 是 BF16，则改成：

```python
rtol = 0.0078125
atol = 0.0001
```

当前没有 rope，输出 dtype 是 FP16，所以使用默认：

```text
rtol = 0.005
atol = 0.000025
```

### 7.3 第一层判断：torch.isclose

核心判断：

```python
torch.isclose(real_float, expect_float, rtol=rtol, atol=atol, equal_nan=True)
```

白话就是每个元素都检查：

```text
abs(NPU - CPU) <= atol + rtol * abs(CPU)
```

通过的元素越多，精度越好。

### 7.4 第二层判断：通过率

```python
fulfill_percent = 正确元素数 / 总元素数 * 100
pct_thd = (1 - 0.005) * 100 = 99.5%
```

也就是说，至少 99.5% 的元素要通过 `isclose`。

当前输出只有 128 个元素，所以允许失败的元素数非常少：

```text
128 * 0.5% = 0.64
```

实际理解时可以认为：基本上不能有元素失败。

### 7.5 第三层判断：最大归一化误差

对于失败元素，还会算一个归一化误差：

```python
diff_abs = abs(expect - real)
b = max(abs(real), abs(expect), (1 / 2^14) / diff_thd) + EPS
err_diff = diff_abs / b
```

如果：

```text
max(err_diff) >= 10
```

也会判 Failed。

所以最终 Pass 需要同时满足：

```text
1. shape 一样
2. 至少 99.5% 元素满足 rtol/atol
3. 最大归一化误差不能超过 10
```

### 7.6 日志会打印什么

`display_output_torch()` 会打印输出表。

如果元素数不超过 20，会全量打印。否则只打印：

```text
前 10 个元素
...
后 10 个元素
```

如果失败，会额外打印：

- 失败元素的位置。
- CPU 期望值。
- NPU 实际值。
- 绝对误差。
- 相对误差。
- 最大相对误差所在行。

## 8. 当前 case 的完整数据流

把当前打开的 case 串起来看，就是这样：

```text
1. run_mxfp8_cases.py 启动
2. 取唯一打开的 case
3. run_mxfp8_case() 写全局配置
4. generate_data() 生成:
   q_fp16 [1,1,1,128]
   k_fp16 [1,1,256,128]
   v_fp16 [1,1,256,128]
5. 计算 scale:
   q_scale [1,1,1,4]
   k_scale [1,1,256,4]
   v_scale [1,1,8,128]
6. 转 FP8:
   q_fp8 [1,1,1,128]
   k_fp8 [1,1,256,128]
   v_fp8 [1,1,256,128]
7. 生成 PA block_table:
   block_table [1,1]
8. CPU golden:
   Q 切 1 块
   K 切 2 块
   V 切 1 块
   计算 attention 输出 cpu_out [1,1,1,128]
9. NPU 准备:
   q 转 TND: [1,1,128]
   k/v 转 PA cache: [1,1,512,128]
   q_scale 转 N2TGD e8m0
   k/v scale 转 PA e8m0
   mask 转 NPU
   block_table 转 NPU
10. 调用 torch_npu.npu_fused_infer_attention_score_v2
11. NPU 输出 atten_out [1,1,128]
12. CPU 输出转 TND [1,1,128]
13. check_result 拉平成 128 个元素逐个比较
```

## 9. 几个容易踩坑的点

### 9.1 `run_npu` 参数目前没有生效

`run_mxfp8_case()` 的函数签名是：

```python
def run_mxfp8_case(case=None, run_npu=False, dump_dir=None, catch_npu_error=False):
```

但函数里面没有根据 `run_npu` 决定是否跳过 NPU。现在无论传 True 还是 False，都会执行：

```python
atten_out, lse_out = npu_mxfp8_fa(...)
```

所以这份脚本当前不能通过 `run_npu=False` 只跑 CPU golden。

### 9.2 `catch_npu_error` 目前没有生效

虽然入口传了：

```python
catch_npu_error=True
```

但 `run_mxfp8_case()` 里没有 try/except 使用它。所以 NPU 报错时不会被捕获成“跳过 NPU”，而是会直接抛异常。

### 9.3 case 里的 `scale` 当前没有真正参与计算

case 里有：

```python
"scale": 0.08838834764831843
```

`run_mxfp8_case()` 会写：

```python
SCALE_VALUE = float(case["scale"])
```

但是后续实际使用的是：

```python
softmax_scale = 1 / sqrt(D + D_rope)
p_scale = torch.tensor([P_SCALE])
```

其中 `P_SCALE` 是全局常量，默认 `1.0`。`SCALE_VALUE` 后面没有被继续使用。

所以你改 case 里的 `"scale"`，当前代码的核心计算大概率不会变。

### 9.4 case 里的 `block_size` 当前没有写回全局 BLOCK_SIZE

case 里有：

```python
"block_size": 512
```

但是 `run_mxfp8_case()` 没有：

```python
BLOCK_SIZE = case["block_size"]
```

当前刚好全局默认也是：

```python
BLOCK_SIZE = 512
```

所以这个 case 看不出问题。如果你以后把 case 里的 `block_size` 改成别的值，代码不一定跟着变。

### 9.5 注释掉的 BNSD case 现在直接打开会报错

`run_mxfp8_case()` 里有强校验：

```python
if INPUT_LAYOUT != "TND":
    raise ValueError("FP8 per-block currently expects input_layout=TND")
```

所以注释里那些 `"layout": "BNSD"` 的 case，直接取消注释不一定能跑。

### 9.6 `run_mxfp8_case()` 当前没有 return 汇总结果

`run_mxfp8_cases.py` 里写了：

```python
result = run_mxfp8_case(...)
```

但 `run_mxfp8_case()` 最后没有 `return result`。所以这里的 `result` 实际是 `None`。

对比结果只是通过日志打印出来，不会返回给上层统计。

## 10. 一句话理解这套脚本

你可以把它想成一条验算流水线：

```text
造一批固定随机数
  -> 按 MXFP8 规则量化成 FP8
  -> CPU 用 PyTorch 手写一遍近似 NPU 内部流水的 Flash Attention
  -> 把同样的 FP8 数据和 e8m0 scale 喂给 NPU 算子
  -> CPU 输出转成和 NPU 一样的 TND layout
  -> 拉平成一维，逐元素比较误差
  -> 达到 99.5% 通过率且最大误差不过线，就 Pass
```

最关键的理解点有三个：

1. CPU golden 不是简单 `softmax(QK^T)V`，而是在模拟分块、量化、online softmax 的算子行为。
2. Q/K/V 虽然都叫 MXFP8，但 scale 分组方式不同：Q/K 按 D 每 32 个一组，V 按 S 每 32 个 token 一组。
3. NPU 调用前的数据整理很重要，尤其是 TND layout、PA cache、block_table、e8m0 scale packing，这些 shape 对不上就会直接影响结果。
