## 0. 关键概念修正

### n_ ≠ active_num

| 变量 | 含义 | 来源 |
|------|------|------|
| `n_` | **T**（token 数，xShape 第 0 维） | `moe_init_routing_v3_tiling_arch35.cpp:1219` |
| `k_` | **K**（topk，expertIdx 第 1 维） | tiling 读取 |
| `totalLength_` | **active_num = T×K** | `n_ * k_` (line 1226) |
| `activeNum_` 属性 | **= T×K，但不使用** | line 1264 注释：「出于历史调用的兼容性，保留校验 activeNum=n*k，但实际上不使用该属性」 |

**IsCountingSortApplicable() 使用 n_（=T），不是 active_num（=T×K）。**

- T 范围检查：`n_ ∈ [CS_MIN_N=256, CS_MAX_N=1024×1024]`（line 2287）
- dropless AER 约束：`actualExpertNum × 2 ≤ expertNum_` 或 `actualExpertNum == expertNum_`（line 2309-2312）
- **tiling 中无 active_num ≥ 20000 的拦截条件**

### v1.x 结论的错误

v1.x 文档将 CutOrigin dropless+GATHER 的优化归因为 `active_num (T×K) ≥ 20000`。该假设：
1. 混淆了 `n_`（=T）和 `active_num`（=T×K）
2. 稳定性测试数据解析错误（log 行错位），导致 11 条用例中 10 条标记为 "NOISY"
3. 重新解析后（使用 `_ti\d+\s+OnReturning` 模式匹配），**11/11 用例 CV < 2%，全部可靠**

## 3. 根因分析

### 为什么 K 决定优化方向

CutOrigin 的三阶段流水线中，**Phase C（GatherAndWrite）** 是关键：

| 路径 | Phase C 行为 | 并行度 |
|------|-------------|--------|
| **CS CutOrigin** | 按计数排序后的顺序，逐行 DataCopy x 行到 expandedX（双缓冲 ping-pong）| active_num 行 |
| **builtin 11000000** | sort 后按顺序写出 | active_num 行 |

CS 的 Phase C 双缓冲要求相邻行 MTE3 写出与 MTE2 载入重叠：

- **K=1**：active_num = T，每核 perCoreTokens 行（如 T=9000 → 141 行/核）。行数少，DMA pipeline 填不满，双缓冲 stall 占比高。
- **K≥4**：active_num = T×K，每核 perCoreTokens×K 行（如 T=2560,K=4 → 160 行/核）。行数多，pipeline 充分填满，MTE2-MTE3 重叠隐藏延迟。

同时，CS Phase A 的 O(coreEntries) 计数排序在 K 大时（coreEntries=T×K/核数 大）相对 builtin sort 的 O(coreEntries × log(coreEntries)) 有更大算法优势。

### 为什么 H 影响幅度

Phase C 每行搬运 H×dtypeSize 字节。H 越大：
- 单行搬运延迟越长 → 双缓冲重叠收益越大
- DMA setup 固定开销被更多数据摊薄

H=4096 单行搬运延迟不足以覆盖 pipeline 切换开销，双缓冲收益近消失。
