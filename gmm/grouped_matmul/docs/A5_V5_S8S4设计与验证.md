# A5 GroupedMatmul V5 S8S4 设计与验证方案

## 1. 文档状态

- 适用芯片：Ascend A5 / ascend950
- 适用算子：`aclnnGroupedMatmulV5`、`aclnnGroupedMatmulWeightNz`
- 目标场景：S8S4 per-channel 与 per-group
- 更新时间：2026-07-25
- 当前状态：
  - per-channel（`offset` 非空）：Host、Kernel、定向编译、隔离部署和通过 V5 接口的 ND/NZ 实卡精度已打通；
  - WeightNz ACLNN 入口：专用前端分类、NZ per-channel OpAPI UT 和真实 ACLNN 上板调用已接通，NZ per-channel 基线精度已通过；
  - per-group（`offset` 为空）：Host tiling、key、资源框架和二进制分支已接入，数值 Kernel 尚未完成。

本文描述 A5 S8S4 的总体设计。per-channel 章节记录当前已经实现并验证的方案；per-group 章节记录已经落地的公共框架、当前占位状态和后续数值 Kernel 的实现要求。两条路径都属于最终交付范围，不包含 A3 MSD 算法。

## 2. 背景与问题

A3 的 S8S4 实现迁移到 A5 后，主要遇到三个问题。

### 2.1 全核同步卡死

S8S4 计算前需要所有 AIV 完成：

1. signed INT4 weight 展开为 INT8；
2. 计算 activation 每行的 `rowSum`。

随后 AIC 才能读取展开后的 weight，AIV epilogue 才能读取 `rowSum`。该阶段使用全核同步。如果 Host 采用普通分批调度，先驻留的核会等待尚未调度的核，造成卡死。

另外，前处理 `TPipe` 的释放时机不能依赖临时对象析构。当前采用显式顺序：

```cpp
weightPreprocess(...);
rowSumPreprocess(...);
AscendC::SyncAll<false>();
pipe->Reset();
```

即先保证所有前处理 GM 写入对全部 Cube/Vector 消费者可见，再释放前处理的 UB 和 pipe 控制状态。

### 2.2 B 的 L1 物理 footprint 被低估

原实现按逻辑大小 `kBL1 × baseN` 给 B 分配 L1。INT8 B 在 L1 中实际采用 NZ 物理布局，其 N 方向需要按 32 对齐：

```text
B_L1 = Align(kBL1, 16) × Align(baseN, 32)
```

例如 `baseN=16, kBL1=256`：

```text
错误逻辑大小：256 × 16 = 4096 B
真实物理大小：256 × 32 = 8192 B
```

scale 紧跟在 B 后面时，B 的 MTE2 写入会覆盖 scale，造成 FixPipe 读到 Inf/NaN，最终出现饱和值或全零。

### 2.3 RowSum 写回方式不正确

`rowSum` 是 AIV epilogue 的 GM 输入，不能依赖 `GlobalTensor::SetValue` 完成单标量写入。当前实现使用：

```text
ReduceSum in UB
    → V_MTE3
    → DataCopyPad UB→GM
    → MTE3_V
```

确保后续 GM→UB 的 MTE2 能正确读取。

## 3. 接口与范围

### 3.1 S8S4 接口数据合同

下表描述 ACLNN/Host 可见的逻辑数据合同。`x`、`weight`、`bias`、`scale` 和 `out` 在
V5 原型中是 TensorList；本路径只接受长度为 1 的 `x/weight/scale/out`，因此表中省略
TensorList 外层。`groupList`、`perTokenScale` 是单 Tensor，`groupType/groupListType`
等是算子属性，不应与 GM Tensor 混写。

| 角色 | 参数 | dtype | 逻辑 shape | GM format | 当前 A5 语义 |
|---|---|---|---|---|---|
| 输入 | `x`（A） | INT8 | `[M,K]` | ND | 激活矩阵，不支持转置 |
| 输入 | `weight`（B） | INT4；兼容 packed INT32 carrier | 普通路径 `[E,K,N]` | ND / FRACTAL_NZ | signed INT4 权重；一个 INT32 物理元素承载 8 个 INT4 |
| 输入 | `bias` | FLOAT32 | `[E,N]` | ND | 公开接口要求的离线辅助量；当前 A5 signed-W4 Kernel 不读取、不送入 Cube |
| 输入 | `scale` | UINT64 | per-channel `[E,1,N]`；per-group `[E,K/256,N]` | ND | weight scale；UINT64 为 FixPipe 使用的编码格式，不是普通 FLOAT64 |
| 输入 | `offset` | FLOAT32 / null | 非空时 `[E,1,N]` | ND | 非对称分支的 `antiquantOffset × scale`；为空时选择对称 per-group 分支 |
| 输入 | `antiquantScale` | null | - | - | S8S4 固定模板不使用 |
| 输入 | `antiquantOffset` | null | - | - | 与 `offset` 不是同一个参数；S8S4 固定模板不使用 |
| 输入 | `perTokenScale` | FLOAT32 | `[M]` | ND | activation 的 per-token 反量化 scale |
| 输入 | `groupList` | INT64 | `[E]` | ND | 每个 expert 的 token 数；当前固定按 count 模式解释 |
| 输入 | `activationInput` | null | - | - | `actType=0`，不融合激活 |
| 输入 | `activationQuantScale` | null | - | - | `actType=0`，不使用 |
| 输入 | `activationQuantOffset` | null | - | - | `actType=0`，不使用 |
| 属性 | `groupListType` | INT64 | 标量 | - | 对 S8S4 固定模板不生效；实现无条件按 `1`（count）执行 |
| 属性 | `groupType` | INT64 | 标量 | - | 必须为 `0`，沿 M 轴分组 |
| 属性 | `actType` | INT64 | 标量 | - | 必须为 `0`，不融合激活 |
| 输出 | `out`（C） | FLOAT16 / BFLOAT16 | `[M,N]` | ND | per-channel 非对称当前仅完成 FLOAT16；per-group 两种 dtype 的数值 Kernel 均待完成 |

其中：

```text
E = expert 数 = weight.shape[0] = groupList.shape[0]
M = 总 token 数 = Σ groupList[e]
K = x.shape[1] = weight.shape[1]
N = weight.shape[2] = out.shape[1]
```

特殊权重格式模板不是 `transposeWeight=true`。当 `tuningConfig[1]=1` 时，调用方提供逻辑
shape `[E,N,K]` 的 weight，并先做 ND2NZ；Kernel 再按该特殊 NZ 物理布局读取。算子属性仍要求
`transposeWeight=false`。

`bias` 在 A3 MSD 合同中的离线定义为沿 K 轴累加 `8 × weight × scale`。A5 当前实现直接把
signed INT4 符号扩展为 signed INT8，不做 `+8` 平移，因此计算不需要该 correction，且
`mmTilingData.isBias=0`。在公开接口合同调整前，调用方仍应传入合法 dtype/shape 和合同兼容
的 bias，不能根据“Kernel 当前不读取”推导出 bias 可以传空。

当前 Host 还要求：

- `groupType=0`、`actType=0`；
- `x`、`weight` 不转置；
- `x/weight/scale` TensorList 长度为 1；
- `x` 为二维，weight 为三维；
- `N > 0` 且 `N % 8 == 0`；
- `antiquantScale`、`antiquantOffset` 为空；
- `groupListType` 在该路径中固定按 1 处理。

普通 NZ 通过 ACLNN V5 调用时还有更严格的前置校验：

```text
K % 16 == 0
N % 64 == 0
```

因此 ND 支持的 `N=8/16/24` 不能直接作为 NZ 正向精度用例；不满足对齐的 NZ 输入会在下核前被 ACLNN 拒绝。

#### 3.1.1 `groupListType` 语义边界

GroupedMatmul 公共能力中定义了三种格式，但当前 A5 S8S4 固定模板只实现 count 语义：

| `groupListType` | 公共语义 | 公共 shape | 示例 | A5 S8S4 固定模板 |
|---:|---|---|---|---|
| `0` | cumsum，元素是各组的累计**结束偏移** | `[G]` | `[64,128,256]` 对应 `M=[64,64,128]` | 不支持 |
| `1` | count，元素是各组的 token 数 | `[G]` | `[64,64,128]` | 唯一支持的执行语义 |
| `2` | sparse，每行是 `[expertIdx, tokenCount]` | `[G,2]` | `[[2,64],[0,128],[5,32]]` | 不支持 |

cumsum 不是“起始偏移数组”，因此不带前导 0；第 0 组长度为 `groupList[0]`，后续组长度为
`groupList[g]-groupList[g-1]`。sparse 中 token 在 `x/out` 里的分段顺序由行顺序决定，
`expertIdx` 选择使用哪一组 weight。

当前 S8S4 Host tiling 会把 `groupListType` 强制写成 1；A5 固定模板的专用 OpAPI 分类也会对
非 1 值直接报错。旧的非固定模板兼容路径仍可能只给 warning，但这不表示可以传入 cumsum
或 sparse 数据：Kernel 会把一维元素逐个当作 count，二维 sparse 输入还会与 Host 的一维
shape 校验冲突。因此本文后续统一使用：

```text
groupListType = 1
groupList.shape = [E]
Σ groupList[e] = M
```

### 3.2 Per-channel 计算公式

对 expert `e` 的第 `m` 个 token、输出列 `n`：

```text
rowSum[m] = Σ x[m,k]

acc[m,n] = Σ x[m,k] × SignExtendInt4(weight[e,k,n])

fixpipe[m,n] = FP16(acc[m,n] × scale[e,0,n])

out[m,n] =
    FP16((FP32(fixpipe[m,n])
          + rowSum[m] × offset[e,0,n])
         × perTokenScale[m])
```

weight 在进入 Cube 前直接从 signed INT4 符号扩展为 signed INT8，不做 `+8` 平移。因此 A3 MSD 使用的离线 bias 不参与 A5 Cube 计算：

```cpp
mmTilingData.isBias = 0;
```

bias 只保留在 ACLNN 接口合同中，不占当前 Cube L1。

### 3.3 待完成的 per-group 输入输出与目标公式

per-group 对应 `offset` 为空的场景：

| 参数 | dtype | shape / format | 说明 |
|---|---|---|---|
| `x` | INT8 | `[M,K]`, ND | 不转置 |
| `weight` | INT4 或 packed INT32 | `[E,K,N]`, ND/NZ | 与 per-channel 共用输入格式 |
| `bias` | FLOAT32 | `[E,N]` | API 合同要求存在，A5 signed W4 路径不送入 Cube |
| `scale` | UINT64 | `[E,K/256,N]` | 每 256 个 K 元素一组，同时保留 N 方向 per-channel scale |
| `offset` | null | - | per-group 当前只设计对称量化 |
| `perTokenScale` | FLOAT32 | `[M]` | 每 token scale |
| `groupList` | INT64 | `[E]` | 每个 expert 的 token 数，固定 count 语义 |
| `out` | FLOAT16/BFLOAT16 | `[M,N]` | Host 已接受，数值 Kernel 待分别接通 |

约束：

```text
quantGroupSize = 256
K % 256 == 0
K <= 18432
N % 8 == 0
```

目标数学表达为：

```text
groupAcc[g,m,n] =
    Σ x[m,k] × SignExtendInt4(weight[e,k,n])
    k ∈ [g×256, (g+1)×256)

dequant[g,m,n] =
    groupAcc[g,m,n] × scale[e,g,n]

out[m,n] =
    perTokenScale[m] × Σ dequant[g,m,n]
```

per-group 没有 offset correction，因此不需要 `rowSum`。数值 Kernel 需要解决各 K group 的 FixPipe 后累加策略及 FP16/BF16 输出精度，不能继续使用当前空占位函数。

### 3.4 ACLNN OpAPI 前端层

`gmm/grouped_matmul/op_api/aclnn_grouped_matmul.cpp` 位于用户接口和算子 Host tiling 之间。它不选择
`baseM/baseN/baseK`，但负责确定 Host tiling 最终看到的 Tensor 元数据和参数，因此属于 S8S4
完整设计的一部分。

V5 S8S4 的调用链为：

```text
aclnnGroupedMatmulV5GetWorkspaceSize
  ├─ CheckNotNull / CheckCommonParam
  ├─ packed INT32 weight: UnpackB32ToB4
  └─ aclnnGroupedMatmulGetWorkspaceSizeCommon
       ├─ 构造 GroupedMatmulParams
       ├─ scale INT64 元数据归一化为 UINT64
       ├─ 空 Tensor/TensorList 归一化为 nullptr
       ├─ CheckParam
       │    └─ CheckFunctionParams
       │         └─ CheckS8S4QuantParams
       └─ GetGMMResultByL0Api
            ├─ contiguous / transpose 视图规范化
            ├─ 建立或恢复 NZ view/storage shape
            ├─ TransWeightToNz 前置格式与对齐检查
            └─ l0op::GroupedMatmul
                 └─ 图编译与 GroupedS8S4BasicApiTiling
```

`UnpackB32ToB4` 不是在 Host 上逐元素解包。它把 packed INT32 Tensor 的逻辑 dtype 改为 INT4，
把对应逻辑维扩大 8 倍，并同步修正 NZ storage shape 或转置 stride；真正的 signed INT4→INT8
展开仍由 Kernel weight preprocess 完成。这是共享 ACLNN OpAPI 中已有的 A2/A3 兼容方式，
不是 A5 新增的数据编码：A3 S8S4 Kernel 同样把输入 GM 绑定成 `GlobalTensor<int4b_t>`，
再由 `GMMS8S4FakeQuantPreProcess` 展开到 INT8 workspace。

对 NZ 输入，OpAPI 保留逻辑 view shape，并恢复用户传入的物理 storage shape。这样 Host tiling
可以按逻辑 `[E,K,N]` 做矩阵参数校验，同时按真实 NZ storage shape 做容量检查。普通 INT4 NZ
的前置对齐合同位于 `TransWeightToNzCheckAlign`：

```text
K % 16 == 0
N % 64 == 0
```

这解释了为什么部分满足 Kernel `N%8==0` 的小 N 用例会在进入 Host tiling 或下核前被 ACLNN
拒绝。

DAV3510 的固定模板由 `IsS8S4FixedTemplateDAV3510` 提前识别，再进入
`CheckS8S4FixedTemplateDAV3510` 做硬校验。识别条件包含 V5/WeightNz、`x=INT8`、
`weight=INT4` 和 `scale=UINT64`，因此不会接管旧 WeightNz 的 `scale=FLOAT32` 伪量化场景。
专用 checker 同时覆盖 per-channel 和 per-group：

```text
单 TensorList：x/weight/bias/scale/perTokenScale/out，offset 非空时也必须长度为 1
groupType=0, splitItem=2/3, groupListType=1, actType=0, 不转置
scale != nullptr, dtype=UINT64, shape=[E,K/256,N]
perTokenScale != nullptr, dtype=FLOAT32, shape=[M]
bias != nullptr, dtype=FLOAT32, shape=[E,N]
offset == nullptr
K % 256 == 0, K <= 18432
```

per-channel 则要求 `offset/scale=[E,1,N]`、输出 FP16；per-group 允许 FP16/BF16。模式判断已
改为 `IsS8S4AsymmetricQuant`，只按 offset 是否存在分流，再由专用 checker 校验 offset
shape。这样“offset 非空但 shape 非法”会直接报错，不会误落入 per-group。

### 3.5 WeightNz 接口通路

`aclnnGroupedMatmulWeightNzGetWorkspaceSize` 与 V5 使用不同的 ACLNN `apiVersion`，但进入 L0 后
调用的是同一个 `l0op::GroupedMatmul`：

```text
WeightNz ACLNN
  ├─ packed INT32→逻辑 INT4
  ├─ apiVersion = WeightNz
  ├─ 强制建立 FRACTAL_NZ view
  ├─ 保留/恢复用户传入的 NZ storage shape
  └─ l0op::GroupedMatmul
       └─ GroupedMatmul Host tiling templates

V5 ACLNN + NZ weight
  ├─ apiVersion = V5
  ├─ 识别输入已有的 FRACTAL_NZ storage format
  ├─ 保留/恢复 NZ storage shape
  └─ 同一个 l0op::GroupedMatmul
```

`apiVersion` 不会作为 `l0op::GroupedMatmul` 的输入或属性传入 Host tiling。因此
`GroupedS8S4BasicApiTiling` 无法也不需要区分调用者是 V5 还是 WeightNz；它根据以下数据合同
判定能力：

```text
x = INT8
weight = INT4 或 packed INT32
scale = UINT64
weight format = ND/FRACTAL_NZ
```

WeightNz 会强制产生 FRACTAL_NZ view，所以通过该入口命中固定模板时只能生成 NZ key：

```text
per-channel: 543162881
per-group:   543163137
```

原始阻断点确实在 OpAPI：WeightNz 会先进入旧 DAV3510 weight-quant checker，而旧 S8S4
合同使用 `scale=FLOAT32` 等另一套参数语义，并拒绝当前 offset 非空合同。现在的接通方式为：

1. `IsS8S4FixedTemplateDAV3510` 用“DAV3510 + V5/WeightNz + INT8/INT4 + UINT64 scale”
   识别固定模板，并在旧 quant/weight-quant 分类前分流；
2. V5 允许 ND 或 NZ weight；WeightNz 明确只允许 NZ weight；
3. 固定模板只接受长度为 1 的 TensorList 和 `[E,K,N]` 逻辑 view；特殊模板仍按
   `tuningConfig[1]=1` 接受 `[E,N,K]` 后转换得到的 NZ；
4. S8S4 输出推形同步读取 `tuningConfig[1]`：普通格式从 weight 第 2 维取得 N，特殊
   `[E,N,K]` 格式从第 1 维取得 N，避免在进入 tiling 前把输出错误推成 `[M,K]`；
5. WeightNz per-channel 要求 `quantGroupSize=0`，per-group 要求 `quantGroupSize=256`；
6. 现有 `scale=FLOAT32` 或使用 antiquantScale 的 WeightNz 场景不满足识别条件，继续走旧
   checker，不改变已有行为；
7. Host tiling、tiling key、tiling data 和 Kernel 均不感知 ACLNN apiVersion，因此不需要改动。

这里参考了 `origin/gmm-s8s4` 的“在旧 checker 前增加专用分流”结构，但没有照搬其合同。远端
允许 weight/scale 多 Tensor、要求 `K%64==0`，并把 V5/WeightNz 与 ND/NZ 一一绑定；本地
固定 tiling 的正确合同是单 Tensor、per-channel 支持 K tail、V5 保留 ND/NZ，而 WeightNz
只新增 NZ 入口。实现以本地 Host/Kernel 能力为准。

## 4. 总体架构

### 4.1 已完成的 per-channel 流水

```text
V5 / WeightNz ACLNN OpAPI
  ├─ packed INT32→INT4 逻辑元数据
  ├─ 可选参数、dtype、shape 和 format 前置校验
  ├─ contiguous / transpose 视图规范化
  └─ 保留逻辑 NZ view 与真实 storage shape

Host tiling
  ├─ 校验 dtype/shape/format
  ├─ 选择固定 tile
  ├─ 用统一模型校验 L1/L0A/L0B/L0C/UB
  ├─ 计算三段用户 workspace
  ├─ 设置 schedule mode 1
  └─ 生成 ND/NZ per-channel tiling key

Kernel
  ├─ AIV: W4 → W8，写 expanded-weight workspace
  ├─ AIV: ReduceSum(X row)，MTE3 写 rowSum workspace
  ├─ SyncAll<false>()
  ├─ TPipe::Reset()
  ├─ AIC: GM→L1→L0A/L0B→MMAD→FixPipe→tile workspace
  ├─ mode-2 AIC→AIV 通知
  ├─ AIV: tile/rowSum/offset/perTokenScale GM→UB
  ├─ AIV: offset correction + per-token scale
  ├─ AIV: UB→GM(out)
  └─ mode-2 AIV→AIC 通知
```

APT 使用专用 facade：

```text
ops-transformer adapter
    → ops-tensor GmmS8S4PerChannel
        → GmmS8S4WeightPreprocess
        → GmmS8S4RowSumPreprocess
        → BlockMmad<MatmulWithScaleFixpipeQuant>
        → BlockEpilogueGmmS8S4
```

### 4.2 Per-group 目标流水

per-group 复用固定 tile、片上资源模型、ND/NZ weight 预处理、BlockMmad 和 AIC/AIV mode-2 协同，但不执行 RowSum：

```text
AIV: W4 → W8，写 expanded-weight workspace
全核同步并 Reset 前处理 pipe

for each K group (256):
  AIC: INT8 MMAD 得到该组 INT32 L0C
  AIC: FixPipe 使用 scale[e,g,n] 得到该组反量化结果
  AIC: 首组写入、后续组累加到 tile workspace

AIV:
  读取完整 tile
  乘 perTokenScale
  写最终 FP16/BF16 out
```

当前 ops-tensor 通用 Kernel 中已经保留 K-group loop 和后续 group 的 atomic-add 骨架，但 ops-transformer 尚未调用一个可用的 per-group facade，累加精度和 BF16 输出也没有完成验证。

## 5. Tiling 与路由

### 5.1 Tiling key

现有 key 和 ABI 不改变：

| weight format | quant mode | key |
|---|---|---:|
| ND | per-channel | `543162880` / `0x20600200` |
| NZ | per-channel | `543162881` / `0x20600201` |
| ND | per-group | `543163136` / `0x20600300` |
| NZ | per-group | `543163137` / `0x20600301` |

四个 key 都属于最终 S8S4 设计。当前只有前两个 per-channel key 完成真实数值验收；后两个 per-group key 已生成二进制分支，但仍是非数值占位。

### 5.2 固定 tile

Host 保持固定模板策略：

```text
baseM = AlignUp(min(M, 256), 16)
baseN = AlignUp(min(N, 256), 16)
baseK = 128
kAL1  = 256
kBL1  = 256
L1 buffer num = 2
```

不因为局部资源不足而静默缩块，也不退化为单缓冲。任一资源不满足时，Host tiling 直接失败并打印实际需求和硬件容量。

L0C 根据实际 tile 决定：

```text
if 2 × L0C_tile <= L0C_size:
    dbL0C = 2
else:
    dbL0C = 1
```

最大 `256×256` tile 使用单 L0C buffer。

### 5.3 调度模式

per-channel offset 非空路径设置：

```cpp
context_->SetScheduleMode(1);
```

这是全核 `SyncAll` 的必要 Host 配套，确保所有参与核同时驻留，避免分 wave 调度造成等待未驻留核。

per-group 数值 Kernel 如果复用“全 AIV weight 预处理 + `SyncAll`”结构，也必须将 schedule mode 1 扩展到 per-group，不能只在 per-channel 设置。

### 5.4 Per-group 当前代码状态

已经完成：

- Host 通过 `offset` 是否为空识别 per-group/per-channel；
- per-group scale shape 校验为 `[E,K/256,N]`；
- `K%256==0`、`K<=18432` 校验；
- ND/NZ per-group tiling key；
- 固定 `baseM/baseN/baseK` 和统一 L1/L0/UB 资源校验；
- `GMMS8S4BasicApiTilingData` 注册；
- APT 编译期 per-group/per-channel 分支互斥；
- per-group `.o/.json` 可生成。

尚未完成：

- `enableWeightPreprocess` 当前只对 per-channel 打开；
- per-group 用户 workspace 当前没有按真实数值流水规划；
- APT 的 per-group 分支调用 `InvokeGmmS8S4V5Materialize()`，函数体只消费参数，不写 workspace 或 `y`；
- 没有可调用的 per-group adapter/facade；
- 多 K-group 的反量化结果累加、最终 perTokenScale 和 BF16 输出未完成；
- 没有 per-group 实卡精度和性能结果。

因此现在不能把 per-group key“能编译、能选中”解释为算子已经支持 per-group 数值计算。

## 6. 统一片上资源模型

Host tiling 和 Kernel BlockMmad 共用 ops-tensor 中不依赖设备运行时的 constexpr 工具：

```text
blaze/gemm/utils/s8s4_fixed_tile_resource.h
```

这样可以避免 Host 按逻辑 shape、Kernel 按物理 NZ footprint 分别计算导致的不一致。

### 6.1 L1 公式

非转置 INT8 A/B：

```text
A_L1     = Align(baseM,16) × Align(kAL1,32)
B_L1     = Align(kBL1,16) × Align(baseN,32)
Scale_L1 = Align(baseN × sizeof(uint64_t),32)

Stage_L1 =
    Align(A_L1,32)
  + Align(B_L1,32)
  + Scale_L1
```

每个双缓冲 stage 独占半片 L1：

```text
stage0Base = 0
stage1Base = L1Size / 2

AOffset     = stageBase
BOffset     = AOffset + A_L1
ScaleOffset = BOffset + B_L1
```

约束：

```text
Stage_L1 <= L1Size / 2
```

`perTokenScale`、`offset` 不在 L1 中，属于 AIV epilogue UB。API bias 在当前 A5 Kernel 中关闭，也不计入 L1。

### 6.2 小 N 回归

对问题 shape `M=8,N=16,K=512`：

```text
baseM=16, baseN=16, kAL1=kBL1=256

A_L1     = 4096 B
B_L1     = 8192 B
Scale_L1 = 128 B
Stage_L1 = 12416 B

stage0:
  A     = [0, 4096)
  B     = [4096, 12288)
  scale = [12288, 12416)
```

B 和 scale 严格不重叠。这是本次 L1 覆盖问题的核心回归。

### 6.3 最大 tile 预算

对 `baseM=256, baseN=256, baseK=128, kAL1=kBL1=256`：

```text
L1:
  A / stage       = 64 KiB
  B / stage       = 64 KiB
  scale / stage   = 2 KiB
  total / stage   = 130 KiB
  double buffer   = 260 KiB < 512 KiB

L0A:
  one tile        = 32 KiB
  ping-pong       = 64 KiB

L0B:
  one tile        = 32 KiB
  ping-pong       = 64 KiB

L0C:
  one INT32 tile  = 256 KiB
  dbL0C           = 1

AIV epilogue UB:
  FixPipe FP16 input   = 128 × 256 × 2 B = 64 KiB
  FP16 output          = 128 × 256 × 2 B = 64 KiB
  perTokenScale        = 128 × 4 B
  rowSum               = 128 × 4 B
  offset               = 256 × 4 B
  total                = 130 KiB < 256 KiB
```

每个 AIC 配对两个 AIV subblock，每个 AIV 只保存 `ceil(baseM/2)` 行，因此最大 epilogue UB 为 130 KiB，而不是按完整 256 行计算。

## 7. Weight 预处理

### 7.1 ND 输入

ND weight 按连续逻辑元素分块：

```text
packed signed INT4
    → Cast FP16
    → Cast INT8
    → MTE3 写 expanded-weight GM
```

每字节两个 INT4，低 nibble 在前。expanded weight 的逻辑布局为 `[E,K,N]` INT8。

### 7.2 普通 NZ 输入

INT4 NZ 物理 shape：

```text
[E, N/64, K/16, 16, 64]
```

块内元素顺序：

```text
[k_in_16][n_in_64]
```

物理索引：

```text
((((e * nBlockNum + n/64) * kBlockNum + k/16)
   * 16 + k%16) * 64 + n%64)
```

预处理把每个 `16×64` INT4 block 拆成两个 `16×32` INT8 NZ block，expanded weight 的 expert stride 为：

```text
Align(K,16) × Align(N,32)
```

### 7.3 特殊 ENK NZ

当 `tuningConfig[1]=1` 时，逻辑 weight 为 `[E,N,K]`，先转换为 NZ 再传入。Kernel 预处理将其转置并统一生成标准 `[E,K,N]` INT8 NZ workspace。

该路径已完成代码、推形通路和 UT 接入，并已纳入三轮实卡约束 Fuzz。当前结果只证明正确性和
确定性，不把特殊 ENK NZ 的性能作为结论。

## 8. RowSum 预处理

所有 AIV 按行分工：

```text
taskIdx   = GetBlockIdx()
taskCount = GetBlockNum() × GetTaskRation()

for row = taskIdx; row < M; row += taskCount:
    process(row)
```

单行处理：

```text
X[row,:] GM→UB
INT8 → FP16 → FP32
ReduceSum
UB→GM by MTE3
```

当前实现一次把整行 K 搬入 UB。按已验收的 `K<=18432`：

```text
x buffer       = 18 KiB
half buffer    = 36 KiB
float buffer   = 72 KiB
reduce work    = 1 KiB
reduce output  = 32 B
total          ≈ 127 KiB
```

ND weight preprocess 的 UB 约 84 KiB，两者在 `pipe->Reset()` 前共存，合计约 211 KiB；NZ preprocess 更小，合计约 134.5 KiB。

当前 Host 对 offset 非空路径没有额外显式限制 K 上限，而 RowSum 使用整行 UB。因此超过已验证 K 范围前，需要补 Host 的 preprocess UB 校验或恢复分块 Reduce；这是当前实现的边界风险。

## 9. Cube、FixPipe 与 scale

### 9.1 Scale 的 L1 使用

scale 在每个输出 tile 前从 GM 搬到 L1：

```cpp
AscendC::LocalTensor<uint64_t> basicScale(
    AscendC::TPosition::A1, scaleL1Offset, baseN);

DataCopyPad(basicScale, basicScaleGm, ...);
```

`A1` 表示该 LocalTensor 位于 L1。FixPipe 使用 `basicScale` 时，由硬件完成后续 scale 通路，不需要 Kernel 显式写一段 L1→FB 搬运代码。

### 9.2 必要同步

scale 生命周期：

```text
Wait FIX_MTE2
GM→L1 scale
MTE2_FIX
FixPipe consume scale
FIX_MTE2
reuse scale buffer
```

MMAD 与 FixPipe：

```text
MMAD complete
M_FIX
FixPipe read L0C
```

保留的关键依赖为：

- `MTE2_FIX/FIX_MTE2`：保护 scale GM→L1 和 FixPipe 消费；
- `M_FIX`：保证 MMAD 完成后 FixPipe 才读取 L0C；
- L1/L0A/L0B 原有 MTE2/MTE1/M 事件。

诊断阶段使用过的 `PIPE_ALL` 已删除。它不能修复地址覆盖，而且会破坏流水性能。

### 9.3 FixPipe 参数

per-channel 路径使用 A5 basic FixPipe vector dequant：

```text
quantPre = VDEQF16
layout   = ROW_MAJOR
input    = INT32 L0C
scale    = UINT64 vector in L1
output   = FP16 per-core GM workspace
```

## 10. AIC/AIV 协同

当前采用同步模式 2：

```cpp
CrossCoreSetFlag<2, PIPE_FIX>(AIC_TO_AIV_FLAG);
CrossCoreWaitFlag(AIC_TO_AIV_FLAG);

CrossCoreSetFlag<2, PIPE_MTE2>(AIV_TO_AIC_FLAG);
CrossCoreWaitFlag(AIV_TO_AIC_FLAG);
```

模式 2 是 AIC 与其配对 Vector task 的直接同步，不采用模式 4 的第二个 Vector `+16` 显式通知方式。

每个 tile 的状态机：

```text
AIC:
  若 slot 已使用，WaitForVector
  MMAD + FixPipe → per-core tile workspace
  NotifyVector

两个 AIV:
  WaitForCube
  subblock0 处理前 ceil(curM/2) 行
  subblock1 处理剩余行
  epilogue → out
  NotifyCube

AIC 退出前:
  WaitForVector 回收最后一个 tile
```

per-core tile workspace 的 slot 通过：

```text
cubeCoreIndex = GetBlockIdx() / GetTaskRation()
```

定位，每个 AIC 独占一个 slot，避免不同 Cube core 之间覆盖。

## 11. AIV Epilogue

AIV 把以下数据搬入 UB：

- FixPipe FP16 tile；
- `perTokenScale[m]`；
- `rowSum[m]`；
- 当前 expert 和 N tile 的 `offset[n]`。

计算：

```text
value = FP32(fixpipe)
value = value + rowSum × offset
value = value × perTokenScale
out   = CastRint<FP16>(value)
```

GM→UB 前使用 `MTE2_V`，UB→GM 前使用 `V_MTE3`，写出后使用 `MTE3_MTE2`，保证下一个 tile 复用 UB 前数据已完成写回。

## 12. GM Workspace

API workspace 的前 16 MiB 是系统保留区。Kernel 通过 `GetUserWorkspace()` 获取用户区。

以下三段布局是已经完成的 per-channel 布局。

workspace 是 Kernel 内部字节区，不是接口 Tensor，也没有单一的 `half` dtype 或
`[coreNum×PARALL_NUM,baseM,baseN]` 逻辑 shape。各 segment 的含义如下：

| segment | 元素类型 | 逻辑内容 | 所有者 / 消费者 |
|---|---|---|---|
| expanded weight | INT8 | ND：`[E,K,N]`；NZ：对应对齐后的物理布局 | AIV 由 W4 展开写入，AIC 的 B 矩阵读取 |
| per-AIC tile slot | FP16 | 每个 AIC 一块 `[baseM,baseN]`，实际有效区为 `[curM,curN]` | AIC FixPipe 写入，两个配对 AIV 分行读取 |
| rowSum | FLOAT32 | `[M]` | AIV preprocess 写入，per-channel epilogue 读取 |

这里的 `aicNum` 是 Cube 核数；每个 AIC 虽然配对两个 AIV subblock，但二者共同消费同一个
tile slot，因此 tile workspace 不能再乘一个 `PARALL_NUM`。per-group 目标布局不含 rowSum，
但 accumulated tile 的元素类型和累加方式仍须由数值方案确定。

所有 segment 按 512B 对齐：

```text
user workspace
  ├─ expanded weight
  ├─ per-AIC FP16 tile slots
  └─ FP32 rowSum[M]
```

### 12.1 Expanded weight

```text
ND expertStride = K × N
NZ expertStride = Align(K,16) × Align(N,32)

expandedWeightSize =
    Align(E × expertStride, 512)
```

### 12.2 Per-AIC tile

```text
tileStride =
    Align(baseM × baseN × sizeof(FP16), 512)

tileWorkspaceSize =
    aicNum × tileStride
```

### 12.3 RowSum

```text
rowSumSize =
    Align(M × sizeof(float), 512)
```

### 12.4 总大小

```text
expandedOffset = 0
tileOffset     = expandedWeightSize
rowSumOffset   = tileOffset + tileWorkspaceSize

userWorkspaceSize =
    rowSumOffset + rowSumSize

ACLNN workspaceSize =
    16 MiB + userWorkspaceSize
```

Host 对乘法、加法、对齐以及 `uint64_t→size_t` 转换做溢出检查。

per-group 目标至少需要：

```text
expanded weight
per-AIC accumulated tile
```

不需要 `rowSum`。如果采用每个 K group FixPipe 后向 FP16/BF16 tile 原子累加，需要评估累加误差；如果改为更高精度中间 workspace，则 Host 和 tiling data 必须同步增加对应容量。该选择应在 per-group Kernel 数值实现时确定，不能沿用当前 `userWorkspaceSize=0` 的占位状态。

特殊 ENK-NZ 分别覆盖 V5/NZ 和 WeightNz/NZ。接入过程中发现推形曾无条件使用 weight
最后一维作为输出 N，使 `[E,N,K]` 被误推为 `[M,K]`。当前推形和空 out fallback 都读取
`tuningConfig[1]`：普通布局取 dim 2，特殊布局取 dim 1；修复后四个特殊布局配置三轮均通过。

覆盖的边界包括：

```text
M = 1,7,8,9,15,16,17,19,20,64,128,255,256,257,
    512,544,768,816,1024,1088,2048,4096,65536
K = 8,16,128,256,512,1024,2048,4096,7160,7168
N = 8,16,64,128,256,1024,2048,4096,7160,7168
E = 1,2,4,8,16,17,64,128
```

三轮策略：

```text
Round 1：固定 manifest 和第一套 seed
Round 2：相同 Shape，替换数据 seed
Round 3：恢复 Round 1 seed，逆序执行
```

最终结果：

```text
Round 1              100 / 100 PASS
Round 2              100 / 100 PASS
Round 3              100 / 100 PASS
总计                 300 / 300 PASS
非零进程退出         0
非预期 Inf/NaN       0
超时/卡死            0
Round 1/3 checksum   100 / 100 一致
```

大数值用例不能继续用固定 `max_abs_error<0.2` 判断。FixPipe 会先把缩放后的 INT32 accumulator
舍入到 FP16，再由 Vector 执行 offset correction；发生抵消时，即使最终结果较小，也会暴露
FixPipe 中间值的 FP16 ULP。Fuzz 验收使用：

```text
tolerance =
    0.2
  + 1.5 × (ULP_FP16(fixpipeGolden) + ULP_FP16(finalGolden))
```

全套最大绝对误差为 `9`，对应样本的允许误差为 `30.2`，且输出有限、ULP 模型内通过。小数值
基线仍维持原来的 `<0.2` 标准。

结果文件：

```text

build_out/s8s4_fuzz_100_full_v2/coverage.tsv
build_out/s8s4_fuzz_100_full_v2/final_summary.tsv
```

### 16.7 验收标准

```text
无卡死
无 Inf/NaN
小数值 max_abs_error < 0.2
大数值满足 FixPipe/最终 FP16 分阶段 ULP 容差
进程正常退出
实际命中目标 ND/NZ binary
相同 seed 重放 checksum 一致
```

## 17. 当前限制与后续项

1. per-channel offset 非空 FP16 路径已完成并验收。
2. WeightNz 专用 OpAPI 分类、NZ per-channel UT 和真实 ACLNN 调用已接通；WeightNz/NZ
   已取得 key/hash 证据，并完成三轮约束 fuzz。
3. WeightNz per-group 参数合同已硬校验，但数值 Kernel 未完成，因此不能用于数值计算。
4. per-group 是最终必须实现的功能；当前只有 Host/key/资源框架，APT 数值分支仍为空占位。
5. per-group 下一步需要完成 weight preprocess、workspace、K-group FixPipe 累加、
   perTokenScale、FP16/BF16 输出和 adapter/facade。
6. per-group 如果采用全核前处理，Host 必须同步设置 schedule mode 1。
7. 普通 NZ 受 ACLNN 前置约束：`K%16==0`、`N%64==0`。
8. packed INT32 已覆盖 10 配置 × 3 轮，特殊 ENK NZ 已覆盖 4 配置 × 3 轮；两者的正确性和
   确定性已验证，专项性能数据仍待补充。
9. RowSum 当前整行占用 UB，应补 per-channel preprocess UB 的 Host 校验，或改为分块 Reduce 后再放宽 K。
10. 性能模板保持 `256/256/128` 和 L1 双缓冲；后续性能回归要求不超过 3%。
11. 当前诊断宏默认关闭，性能测试不得打开 `BLAZE_S8S4_DEBUG`。
