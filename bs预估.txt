原始(非 chunk)模板的 bs 上限由 DispatchBuffInit 阶段卡住(EP≥2 时它一定是瓶颈)。直接给闭式公式。

公式

            8 · (UB − Fixed)
bs_max  =  ────────────────────
            topK · (64 + EP)

其中:
- UB = 单核可用 UB 字节数(平台查得;你说的 256KB → 262144)
- EP = epWorldSize(= worldSize_)
- topK = 路由专家数
- Fixed ≈ 49152 + 4·G + 32·EP,即 6×8KB copyTmp(48KB)+ cumsum 表 + 其它小量;G = moeExpertNum = EP·EPR 是全局专家总数

分母怎么来的(每个 token 吃的 UB 字节)

┌──────────────────────────┬──────────────────────────────────┐
│          tensor          │            字节/token            │
├──────────────────────────┼──────────────────────────────────┤
│ validTopkIndex           │ 4·topK                           │
├──────────────────────────┼──────────────────────────────────┤
│ topkIndex                │ 4·topK                           │
├──────────────────────────┼──────────────────────────────────┤
│ gatherMask = maskSlot×EP │ topK·EP/8                        │
├──────────────────────────┼──────────────────────────────────┤
│ 合计                     │ topK·(8 + EP/8) = topK·(64+EP)/8 │
└──────────────────────────┴──────────────────────────────────┘

gatherMask 那项就是 EP 因子的来源:接收端要把 EP 张源卡的 mask 槽位全摆进 UB。

简化版(丢掉小量,便于估)

bs_max ≈ 8·(UB − 48KB) / (topK·(64 + EP))

代入(UB=256KB,topK=16)

┌─────┬────────┐
│ EP  │ bs_max │
├─────┼────────┤
│ 8   │ ~1,640 │
├─────┼────────┤
│ 16  │ ~1,320 │
├─────┼────────┤
│ 64  │ ~830   │
├─────┼────────┤
│ 256 │ ~320   │
├─────┼────────┤
│ 768 │ ~125   │
└─────┴────────┘

两个补充约束(通常不先到顶,但 h 大时要查)

同一块 UB 还被另外两个阶段复用,bs 取三者最小:

SendAndQuant:  bs ≤ (UB − ~6h − 2KB) / (topK · 8.25)
Unpermute:     bs ≤ (UB − 18h)       / (topK · 4)        ← h 大时这条会反超

h=7168 时 18h≈126KB,Unpermute 单独算约能到 ~1050;但 Dispatch 阶段(上表)更低,所以以 Dispatch 公式为准。一旦 18h > UB(h≳14K @256KB),原始模板任何 bs 都摆不下。

一句话:原始模板 bs_max ≈ 8·(UB−48KB) / (topK·(64+EP)) —— EP 和 topK 都在分母,所以专家并行越大、topK 越大,bs 开得越小。
