dispatch / combine teardown — 编译运行手把手教程

从零把两个 mxfp8 teardown 算子在 A5(Ascend950PR) 上编译、装包、跑通、比对的全流程。每条命令都讲清「干什么 / 为什么 / 在哪跑」。

远端 A5 / 123.60.114.41:20028 CANN /home/0625/env 工程 /home/developer/ops-transformer/experimental/mc2 形态 registry-invoke + aclnn 单卡 · 无 MPI/HCCL

0先建心智模型：四步法

teardown 是 registry-invoke 自定义算子（不是 <<<>>> 直调，因为 A6 不支持直调）。所以分两条线：算子线（编译成算子包、装进 CANN）和 测试线（编译一个调 aclnn 的 C++ 驱动 exe，造数→跑→比对）。

① 编译装包算子
把 kernel+tiling+OpDef 编成算子包并装进 CANN，让 aclnn 能找到
bash build_op.sh dispatch_teardown,combine_teardown
→
② 编译测试驱动
cmake 编出单卡 aclnn C++ 驱动 exe（链接装好的算子 api）
bash build_test.sh
→
③ 跑单个用例
golden 造数 → 清场 → aclnn 上板 → 比对
bash run.sh dispatch 8 8 7168 4 2
→
④ 回归 / 链式
多 shape 回归 + dispatch→combine 串接
bash regress.sh
什么时候重跑哪一步（最常踩）：改了 kernel/tiling/OpDef → 重跑 ①（必须重装包）；只改了 C++ 驱动 → 重跑 ②；只改了 golden/compare(.py) → 直接 ③（python 不用编）。改 ① 后 ② 不必重跑（除非 aclnn 签名变）。

3第①步：编译装包算子 改了 kernel/tiling/OpDef 必重跑

bash build_op.sh dispatch_teardown,combine_teardown

脚本内部两件事：

# 1) 编算子包（--experimental 因为算子在 experimental/ 下；--soc 选 a5 的 ascend950）
cd /home/developer/ops-transformer
bash build.sh --pkg --experimental --soc=ascend950 --ops=dispatch_teardown,combine_teardown -j16

# 2) 装包到 CANN 的 custom_transformer vendor（aclnn 运行时从这里找算子二进制）
./build_out/cann-ops-transformer-custom_linux-*.run --force
  • --ops=a,b 逗号分隔可一次编多个算子。
  • 编一个算子约 1~2 分钟；成功末尾出现 vendors/custom_transformer。
  • 这步是慢环节：所以调业务逻辑时尽量先用 golden 把算法想对，减少重编次数。
编译报错先看：grep -inE "error:|fatal error|undefined" /tmp/bfix.log。常见坑：registry kernel 编译没有 micro_api/、adv_api/ 头（直调工程才有）→ 只能用 basic_api。

4第②步：编译测试驱动 改了 .cpp 驱动 / aclnn 签名才重跑

bash build_test.sh

内部 = cmake 编单卡 aclnn C++ 驱动，产物 build/test_dispatch_teardown 与 build/test_combine_teardown：

cmake -B build -DASCEND_CANN_PACKAGE_PATH=/home/0625/env/ascend-toolkit/latest
cmake --build build -j8

驱动只做：aclInit → setDevice(0) → 读 bin → H2D → aclnnXxxGetWorkspaceSize → malloc → aclnnXxx → 同步 → D2H → 写 *.npu.bin。单卡单进程，无 MPI/HCCL（teardown 纯本地）。

5第③步：跑单个用例

bash run.sh <op> <bs> <topk> <h> <E> <R> [seed]
# 例：真实场景
bash run.sh dispatch 8 8 7168 4 2
bash run.sh combine  8 8 7168 4 2

run.sh 串起四个子步骤：

a. golden 造数
numpy 造 fp8/e8m0/int32 输入 bin + 算 CPU 参考输出 bin
python golden_<op>.py ...
→
b. 清场
npu-smi 看占用 → pkill 残留 → sleep（约束：跑前必清）
pkill -9 python3; sleep 3
→
c. aclnn 上板
驱动 exe 读 bin→跑算子→写 *.npu.bin
build/test_<op>_teardown ...
→
d. 比对
NPU vs golden：fp8/int bit 精确，bf16 看 mae/cos
python compare_<op>.py ...

参数含义：bs token 数 · topk 每 token 选专家数 · h hidden（必须 %32==0，mxfp8 group=32）· E 每卡专家数 · R 卡数。约束：topk ≤ GE=R*E。数据落在 data_<op>_<bs>_..._/。

看懂输出

# dispatch（5 个输出，全 bit 精确）
  [PASS] expand_x(fp8 bytes) exact-equal (n=458752)
  [PASS] expand_scale(e8m0 bytes) exact-equal (n=14336)
  [PASS] send_counts / expand_idx / expert_token_nums exact-equal
=== DISPATCH_TEARDOWN PASS ===
# combine（bf16，反量化加权和，mae≈0）
  [PASS] x mae=0.000e+00 cos=1.000001 (n=57344)
=== COMBINE_TEARDOWN PASS ===

6第④步：回归 & 链式

# 回归集：退化(topk≥E)+稀疏(topk<E)+非1024对齐 h(2560/1536)+链式，一键全跑
bash regress.sh        # 末尾 ALL GREEN 即全过

# 链式：dispatch 在 NPU 真实产出的 expand_idx → 直接喂 combine，验两算子组合
bash run_chain.sh 8 8 7168 4 2
当前实测状态：regress.sh 全绿 9/9（真实场景 + 稀疏 + h=2560/1536 + 链式），dispatch 5 输出 bit 精确、combine x mae=0。

7怎么改场景 / 加用例

  • 换 shape：直接改 run.sh 的 6 个参数即可（算子是参数化的，无需重编算子）。如跑 bash run.sh combine 16 6 2048 8 2 42。
  • 加固定回归档：在 regress.sh 里加一行 run dispatch <...> "tag"。
  • 改 golden 算法 / 造数分布：编辑 golden_*.py，直接重跑 run.sh（python 不编）。
  • 约束：h%32==0（否则 tiling 返回 GRAPH_FAILED）；topk≤R*E；combine 的 topk 决定每专家收到 token 数 ≤ bs。

8常见坑速查

现象根因解
aclnn 161002 basePath.empty没设 ASCEND_CUSTOM_OPP_PATHexport ASCEND_CUSTOM_OPP_PATH=${ASCEND_OPP_PATH}/vendors/custom_transformer（run.sh 已带）
HCCL 建链失败 / 卡占用别人/残留进程占卡跑前清场：npu-smi info; pkill -9 python; sleep 3
kernel 编译 micro_api ... not foundregistry kernel 无 micro_api 头用 basic_api 等价实现（e8m0 反量化用位型 bitcast）
换 h 后 scale/精度静默错scaleH=h/32 非 32B 对齐 + 裸 DataCopy已修为 DataCopyPad；h 仍须 %32==0
tiling 改了没生效改 tiling/kernel 后没重 build_op 装包改算子侧必重跑第①步
只重编一个算子后另一个全挂build_op.sh <单算子> + .run --force 把 vendor 包整个换成只含该算子、挤掉另一个两个算子一起装：build_op.sh dispatch_teardown,combine_teardown

9迁到 A6 要改什么（多核 portable，零代码改动）

核数A5 = 56 V核（实机 Ascend950PR_957c，实测 GetCoreNumAiv()=56、实 launch 56 个 AIV block）· A6 = 28 V核 切分tiling 运行时查 GetCoreNumAiv() → SetBlockDim(min(核数,工作量))，kernel 按 blk/aivNum 均分（dispatch 按行、combine 按 (token,chunk)）→ 不写死核数，A6 自动用 28 核、源码一字不改 编译build.sh --pkg --experimental --soc=ascend910_96 --ops=...（OpDef 已含 ascend910_96 config，白名单 token 一字不差） 复用build_test / run / golden / compare 原样（AIV 算子不区分 a5/a6，单卡无通信） A6 分配真实场景 dispatch 64 行/28 ≈ 2-3 行/核、combine 56 项/28 = 2 项/核 → 利用率好 性能双缓冲在 A5（~1 行/核）无收益已回退；A6（≥2 行/核）会有收益，重做用显式 MTE2/MTE3 软流水（非 TQue 直拷）+ 多跑复验

诚实边界：A5 开发 + 实测全绿（回归 9/9）；A6 尚未实跑（无访问权限），按构造 A6-ready，唯一不确定项是 GetCoreNumAiv()/平台行为在 ascend910_96 是否完全一致（预期一致，本就是该 API 跨平台用途）；拿到 A6 同 harness 复跑即坐实。
