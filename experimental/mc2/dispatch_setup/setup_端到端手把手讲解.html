因 CCU 硬件/API 无法直译的偏离（3 类 + 1 说明，均等价实现、数据布局零偏离）：
  • ① wishCnt 输出（dispatch）— 硬件：CCU 不支持动态地址标量 GM 写（SE 无 StoreVariableAt）。A6-proven 参考也不由 CCU 产 wishCnt。→ 由 driver host 预算（wishCnt 是全卡 expert_ids 的确定性函数）。
  • ② expert_id_2_dst_va_map — CCU 寻址 API：CCU 访存地址 = (VA, token) 对，token 是对端窗口注册的寻址凭证、不能是 host 任意常量，必须运行时经 PreSync（NotifyRecord/Wait）从对端换来。故 docx 的"专家→目的 VA"由 PreSync（基址 VA+token）+ host 预算 routeTable（块内偏移）共同实现；纯 host va_map（只有 VA、无 token）在 CCU 上不可寻址。
  • ③ expert_id_2_dst_notify_va_map — CCU 0.5RTT API：CCU 的 arrive-notify 计数是 per-channel/tag 的 countXn（RecordExpectCount 预告 + WriteNbWithArriveNotify 累加 + WaitallpeersarriveNotify 等待），不是 per-expert 的 Xn 地址。故 docx 的"专家→目的 Xn"由 channel/tag arrive-notify 机制实现。
  • ④（非硬件偏离，说明）：mxfp8 分离 payload/scale 是"全链 mxfp8"要求（docx 原文"mxfp8 量化后面加"）；combine 的 sendCounts→assistTable 是 host 预算簿记决策（同 ① 的硬件因，见 §2）。
  • ⑤ combine 数据区形状 —— 已与 docx 对齐（docx 已修正为 [R*E*bs,h]）：此前 docx combine 输出/输入写 [R*E,h]（漏 *bs），本实现按正确性必需用 [R*E*bs,h]——combine teardown 按 (ge, expand_idx) gather 每 token 副本，每全局专家块须 bs 个槽位；bs>1 时缺 *bs 会同专家多 token 互覆盖、无法做 per-token 加权和。技术总监已修正 docx 为 [R*E*bs,h]，现两侧完全一致（与已测 combine_teardown 字节级自洽）。

2一个关键架构决策：host 预算簿记

★ CCU 硬约束 → 簿记移出 CCU

CCU 不支持动态地址的标量 GM 写（SE 无 StoreVariableAt）。A6-proven 参考因此把所有簿记（wishCnt / expand_idx / dstByteOff 路由）都 host 预算好、传给 CCU。本设计沿用：

  • setup CCU 只搬 token 数据（payload + scale），落点全由 host 预算的 routeTable / assistTable 决定（device 不算 ge/E、不乘法、不写标量）。
  • wishCnt / expand_idx 由 driver host 预算（它有全卡 expert_ids，是确定性函数）。数据布局 100% 对齐 docx（expert-major）与已测 teardown；仅"名义产出方"从 CCU 挪到 host。

3在途数据：mxfp8（payload + scale 两个独立区）

量化在算子外做好，传进来即 mxfp8。每 token = fp8_e4m3fn payload（h 字节） + e8m0 scale（h/32 字节，group=32），是两个独立 GM 区。setup 每 token 做两次跨卡写（payload 一次、scale 一次），落到对端的 dataRegion 与 scaleRegion。

真实场景 h=7168 → 每 token = 7168 字节 payload + 224 字节 scale · A = R·bs·min(topk,E) = 64 行

4dispatch setup CCU：逐 token 跨卡 push

本卡 rank0 有 bs 个 token；每 token 选 topk 个全局专家。setup 把每个复制体写到"拥有该专家的卡"的 expert-major 数据区。

路由与落点（host 预算的 routeTable）

ge = expert_ids[i][j]　→　dstRank = ge/E · le = ge%E
block = le*R + my_rank（expert-major，源卡=my_rank）· pos = 该 ge 出现次数（=expand_idx）
row = block*bs + pos　→　dataDstByteOff = row*h · scaleDstByteOff = row*(h/32)

routeTable[i*topk+j] = {dstRank, dataDstByteOff, scaleDstByteOff}（int64，host 预算）。CCU 读它 → WriteNbWithArriveNotify(channel[dstRank], dataRegionBase[dstRank]+dataDstByteOff, x[i], h 字节, tag)，scale 同理。

CCU Algorithm 段式（照 A6-proven 参考）

1 InitResource(Var/LocalAddr×2/RemoteAddr×2/event/BlockCcuBuf)
2 LoadArgs(顺序=GeneArgs)  2.5 clearallpeersarriveNotify(tag)
3 PreSync(NotifyRecord/Wait 交换对端 data/scale 区 addr+token，4 XN 槽)
5 PreCount(读 routeTable dstRank 累加 sendBytes) → 6 RecordExpectCount(逐对端)
7 DoMainLoop: for i,j { 读 routeTable → CCU_IF(dstRank==r):
     self→LocalCopyNb(payload)+LocalCopyNb(scale) / cross→WriteNbWithArriveNotify×2 }
9 WaitallpeersarriveNotify(R-1)  10 LocalCopyNb 置 ready[0..R)=1

5combine setup CCU：expandX 送回源卡（对称反向）

owner 卡算完专家输出（expandX，expert-major），把每行送回原始源卡的 combine 数据区（每全局专家一块 ge，块内位 = 该 token 的 expand_idx）。

expandX 行 r 属块(le,src) 第 pos 个 → ge = owner*E+le · 送回卡 = src
dataDstByteOff = (ge*bs + pos)*h　→　assistTable[r] = {ownerRank=src, dataDstByteOff, scaleDstByteOff}

host 展开 A 行、每行 CCU_IF(ownerRank==r) 路由；padding 行 ownerRank=哨兵 → 全跳过（cnt<A 的尾部）。段式与 dispatch 同构，独立 tag moe_combine_05rtt。

6CCU 数据面 4 接口（坐实自 ccu_kernel.h + api.h）

WriteNbWithArriveNotify写对端：(channel, RemoteAddr rem, LocalAddr loc, Variable len, tag)，len 字节 atomic-add 到对端 wtCount。唯一跨卡写。 LocalCopyNb写本卡自己：(LocalAddr dst, LocalAddr src, Variable len, &buf, 1, event) + WaitEvent。不能写对端。 RecordExpectCount预告"我会发多少字节"到对端 wishCntXn。 WaitallpeersarriveNotify收方等 totalCntXn 达 target(=R-1)。 clearallpeersarriveNotify清上轮计数（起头必清）。

铁律：类名/签名/大小写逐字一致否则链 SE undefined；Variable 恒 8 字节（routeTable 按 int64 排布步进 8）；LocalAddr/RemoteAddr 的 .token 两端必设；不支持 Variable+立即数（立即数先落 Variable）。

7setup 产出 = teardown 输入（字节级咬合）

setup产出= teardown 输入

8验证状态与诚实边界

已机器验证（a5，纯 C++ host 模型）：地址 math 端到端自检 6/6 全 PASS——模拟 dispatch 放置→teardown 紧密化→combine 送回→combine_teardown gather→重建，每个 token marker 精确往返（含字节偏移/expert-major 块序/块内位/wishCnt 一致）。即 CCU 执行的地址逻辑与已测 teardown 契约端到端自洽。
无法在 a5 验证的部分（硬环境限制，实测铁证）：a5 的 CCU 头/库是与 a6 不同的旧/残缺 API（缺 ccu_kernel_arg.h/ccu_types.h；channels_ 是 private unordered_set；CompletedEvent 无 SetMask）。A6-proven 真实参考在 a5 上同样编不过 → CCU kernel 的编译+上板只能在 A6 做（你无法访问）。CCU 代码验证方式 = 与 a6-proven 参考逐 API 对齐 + 上面地址 math 已验。
待 A6 落地前需 SE 确认：GetRemoteAddr index 语义、WaitallpeersarriveNotify 在"某对端发 0 token"时的 target 语义、CCU_IF/CCU_WHILE 宏细节。
