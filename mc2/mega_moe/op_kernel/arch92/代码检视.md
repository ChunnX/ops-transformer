# MegaMoe Arch35/Arch92 代码检视

**人工检视入口：第 10 节。** 第 1～9 节保留迁移背景、Host 配套及验证事项；不能仅凭这些概述认为 Kernel 侵入式修改已经检视完毕。第 10 节按原有文件、函数和代码段列出修改前后、适配原因、Arch35 保持条件及逐项检查框。

## 1. 对照口径

本文按一个完整迁移结果检视，不把开发过程中的调试改动当成功能修改。当前上游基线为 `a259159c8`；本次将原迁移提交 `9a247e362` 重放到该基线上。旧文档以 `f6baef024` 为基线的文件数量、同步流程和行号已不适用于当前代码。

重放完成后，可用以下命令查看完整差异：

```bash
git diff a259159c8 HEAD -M --name-status -- mc2/mega_moe
git diff a259159c8 HEAD -M -- mc2/mega_moe
```

结构仍为：`arch35` 保留原架构 wave/layered；`arch35_92` 放公共基类、stage、Blaze、Workspace 和 tiling 定义；`arch92` 放 1C1V 入口与独立 wave。公共 Host tiling 在 `op_host/op_tiling/arch35_92`。

**Arch92 的迁移基础仍是去掉 Arch35 A8W4 的 AIV0 权重展开职责，而不是把 Arch35 所有 AIV0 工作都删除。** reset、量化、输入通知、count 读完上报及 count 表清零等公共职责，仍须由唯一 AIV 完成。

## 2. 本次上游新增功能

### 2.1 通信去重

上游 `9f1bacbd5` 引入通信去重。Host 的 `dedupMode` 为 0/1/2/3，分别表示关闭、仅 Combine、仅 Dispatch、两者都开。Dispatch 默认请求后经过收益/容量判断；Combine 由 `combine_comm_mode` 控制，当前只支持 MTE 非量化 Combine。收益判断使用各 rank 一致的 `numMaxTokensPerRank`，不能改为各卡不同的本地 bs。参见 [请求与开关规则](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L337)、[去重参数校验](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L584)。

建表按同一来源卡、同一 token 聚合同卡多个专家的接收行。FIRST 行负责远端拉取后本地分发；LAST 行汇总多个专家的 GMM2 结果并只发送一次。描述符中保留成员行、topK 位置等信息，不能仅修改 Dispatch 而不调整 Combine/Unpermute。参见 [建表入口](../arch35_92/stage/mega_moe_token_dedup.h#L469)、[Dispatch 分流](../arch35_92/stage/mega_moe_token_dispatch_dedup.h#L466)、[Combine 去重消费](../arch35_92/stage/mega_moe_gmm2_combine_dedup.h#L332)。

### 2.2 输入准备与共享 GMM 启动

`1ebb3d59f` 和 `9cc9eeaf5` 调整输入准备、跨卡到达判据及共享计算依赖。入口不再保留旧的 `SyncAll<false>() + SyncInputAcrossRanks()` 流程，而是分别发布 reset 和 token 数据完成事件；count 携带当前轮次标签，接收侧校验整表后才能使用。出口跨卡同步仍保留。参见 [本地输入准备](../arch35_92/mega_moe.h#L941)、[count 到达与前缀和](../arch35_92/stage/mega_moe_token_dispatch.h#L446)、[输出同步与 Unpermute](../arch35_92/mega_moe.h#L1063)。

共享 GMM 的启动条件分为：无共享、直接读取原始预量化输入、依赖 quant/pack 结果。预量化且 H 为 64 的倍数时，共享 GMM 的 MTE2 不必等 MoE pack；其 Scalar 状态访问和 FIX 写 UB 仍有独立依赖。参见 [启动条件](../arch35_92/mega_moe.h#L1048)、[AIC 输入等待](../arch35_92/mega_moe.h#L1029)。Arch92 当前入口仍只实例化 BF16 X，因此未借本次合并扩大到预量化输入。

### 2.3 A8W4 L1 流水

`5b4d40d9a` 将 A8W4 L1 分配移到 Host 计算，并以 `BlockContext` 传递新的 Block/Prologue 生命周期；不能保留旧调用签名而丢掉 `pipeline` 参数。参见 [Host L1 分配](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L2736)、[BlockContext 类型](../arch35_92/common/mega_moe_gmm_common.h#L38)、[GMM1 A8W4 调用](../arch35_92/stage/mega_moe_gmm1_activation.h#L694)、[GMM2 A8W4 调用](../arch35_92/stage/mega_moe_gmm2_combine.h#L935)。

Arch35 保留此新流水；Arch92 当前 generic QGMM 仍不执行 W4→W8 prologue，A8W4 直接混合 FP8/FP4 模式仍不放行。两者不能因共用文件而误实例化同一套 W4 计算对象。

## 4. Host 差异

### 4.1 注册与编译

增加 `ascend910_96` 注册及其编译选项，Arch92 使用 `--cce-auto-sync=on`，Arch35 保持现有设置。参见 [平台注册](../../op_host/mega_moe_def.cpp#L297)、[Arch92 编译选项](../../op_host/CMakeLists.txt#L31)。

Arch92 入口使用 `KERNEL_TYPE_MIX_AIC_1_1`，支持当前启用的 A8W8/A4W4、BF16 输入输出和 MTE；不实例化直接混合 A8W4。参见 [Arch92 入口](./mega_moe_apt.cpp#L74)。

### 4.2 配比、能力与 Workspace

Host 按 9201/9202 识别 Arch92，校验 1C1V；Arch35 校验 1C2V。参见 [平台策略](../../op_host/op_tiling/arch35_92/mega_moe_host_arch_policy.h#L18)、[配比校验](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L2663)。Arch92 能力门保留 A8W8/A4W4 MTE，参见 [能力限制](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L2692)。

Host 提交 Workspace 时与 Kernel 选择同一策略：Arch35 DEFAULT，Arch92 GM_HANDOFF_EXPERT_WAVE。新增 A8W4 L1 layout 的计算也在提交阶段保留，不覆盖这项策略选择。参见 [最终提交](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L2925)。

URMA Combine consumer 数从 `blockAivNum / 2` 改为 `aicNum`，对已校验的 Arch35 等价；Arch92 当前不运行 URMA，不能将此项写成 Arch92 MTE 挂死的直接修复。参见 [Combine 槽容量](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L1391)。

### 4.3 本次补齐的容量一致性

合并时发现 Host 固定 UB 估算漏算去重 prepass ready 区，以及非量化去重 Combine 的 per-expert ready 区；Kernel 已为两者分配并清零。已把这些项补入 Host flag 数量估算，避免 resetTensor 比 Host 估算更大，进而挤占后续 quant/route 缓冲。参见 [Host flag 估算](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L1412)、[Kernel 同源区域](../arch35_92/common/mega_moe_workspace.h#L236)。

prefetch 路径还按 Kernel 的做法取连续 flag 区与 GMM1 tile status 区的最大清零批量。该修正影响容量规划，不改变 Arch35 的执行顺序。参见 [固定 UB 容量](../../op_host/op_tiling/arch35_92/mega_moe_tiling.cpp#L1454)。

## 5. 架构角色与执行策略

硬件策略只描述物理配比/角色：Arch35 AIV0 计算侧、AIV1 路由侧；Arch92 唯一 AIV 同时承担两种角色。它不能把“只有 AIV0 才有的权重展开任务”自动映射成 Arch92 需要执行的任务。参见 [硬件角色定义](../arch35_92/common/mega_moe_arch_policy.h#L29)。

执行策略描述以下差异，都是编译期参数。参见 [执行策略定义](../arch35_92/common/mega_moe_execution_policy.h#L27)。

| 参数 | Arch35 默认 | Arch92 | 原因 |
| --- | --- | --- | --- |
| PERSIST_DISPATCH_CUMSUM | false | true | Arch92 路由与激活复用同一个 UB，后续 wave 需从 GM 恢复 cumsum；与 Arch35 W4 的持久化需求同类。 |
| USE_GM_HANDOFF | false | true | 通用 GMM1 在 Arch92 经 GM 交接给唯一 AIV；不是说 Arch35 所有模式都写 UB，Arch35 A8W4 本来就写 GM。 |
| FP4_SWIGLU_OUTPUT | false | 仅 A4W4 为 true | 当前 Arch92 A4W4 两段 GMM 都用 FP4；Arch35 A4W4 激活输出仍为 FP8。 |
| WORKSPACE_LAYOUT | DEFAULT | GM_HANDOFF_EXPERT_WAVE | 为 GM GMM1 结果、同步、cumsum 和 packed FP4 激活分配一致的布局。 |

Workspace 的新增策略和 FP4 字节数在 [Workspace 布局](../arch35_92/common/mega_moe_workspace.h#L31)；量化类型差异在 [QuantConfig](../arch35_92/common/mega_moe_types.h#L203)。

后续 A8W4 直接接口支持后，A4W4 的 SwiGLU 输出计划与 Arch35 一样改为 FP8、GMM2 使用 A8W4。届时必须同时改类型、packed 地址、Workspace 容量及入口能力门，不能只把策略值改掉。

## 6. 新同步和去重在 1C1V 下的适配

### 6.1 输入通知不能只交给 AIV0

Arch35 有共享时，AIV1 发送 index/count，AIV0 负责向 AIC 通知输入就绪。Arch92 路由角色也是真，如果照搬原 `if AIV1 ... else AIV0` 分支，会只发送而无人通知 AIC。现由唯一 AIV 在 count 发送前，同时完成 AIC 通知；无共享时也只通知一次。参见 [输入准备分支](../arch35_92/mega_moe.h#L969)。

两项 mode 0 全 AIV 事件仍要求每个实际 AIV 各发布/消费一次，空 token 或空专家范围不能跳过。Arch92 不虚构第二个 AIV，也不追加旧入口全核屏障。

### 6.2 GM 交接与 UB 保护

Arch35 保留 INPUT_UB_FREE 的 AIV0 发布和 AIC FIX 等待；Arch92 的 generic GMM1 写 GM，不再需要这组成对的 FIX→UB 保护，因此 set/wait 一起编译期裁掉。reset/token 就绪依赖仍保留。参见 [AIC 等待](../arch35_92/mega_moe.h#L1029)。

唯一 AIV 读取共享 GMM1 GM 结果前，先等自己的输入/count MTE3 搬出结束；进入 MoE count/Dispatch 前再次建立对应的 UB 复用顺序。Arch35 的 AIV0/AIV1 分支不改。参见 [共享阶段 UB 复用](../arch35_92/mega_moe.h#L633)、[MoE 阶段 UB 复用](../arch35_92/mega_moe.h#L659)。

### 6.3 count 表读取、导出、清零

Arch35 AIV1 读取/发布 count；低 hiddenDim 去重时 AIV0 也读取一次，其他 AIV0 只上报 read-done。每个物理 AIV 必须恰好上报一次。Arch92 唯一 AIV 从正常 count 准备路径上报，不再执行 AIV0 的第二次本地建表。参见 [count 准备与 read-done](../arch35_92/stage/mega_moe_token_dispatch.h#L475)。

Arch35 由 block0 AIV1 导出计数、全部 AIV0 分片清零；Arch92 block0 唯一 AIV 导出，全部唯一 AIV 分片清零。所以这里必须是两个可同时成立的条件，不能保留互斥 else-if。全体等 COUNT_TABLE_READ_DONE 后再清零，避免快核破坏慢核尚未读取的原始表。参见 [导出与清零](../arch35_92/mega_moe.h#L915)。

### 6.4 去重 worker 与完成计数

Arch35 在 hiddenDim≤2048 时可让 AIV0 参与：AIV1 worker 为 [0,N)，AIV0 为 [N,2N)；前者完成后加 1，后者加 1<<16。Arch92 只有 N 个 worker，全部从 [0,N) 认领、只加低 16 位。参见 [worker 分工](../arch35_92/stage/mega_moe_token_dedup.h#L404)、[完成上报](../arch35_92/stage/mega_moe_token_dedup.h#L505)。

Dispatch 的高 16 位发布门用于保护 Arch35 AIV0 建表 UB 不被 AIC 提前覆盖；Arch92 没有该角色，跳过此门。Combine 等待值也同步改为 N，不能继续等 N|(N<<16)。参见 [Dispatch 发布门](../arch35_92/stage/mega_moe_token_dispatch_dedup.h#L444)、[Combine 全部建表完成](../arch35_92/stage/mega_moe_gmm2_combine_dedup.h#L270)。

### 6.5 去重 Combine 必须切换通知协议

不开去重的非量化 Combine 仍按 tile 做 credit/ACK；去重开启时改为完整专家就绪后消费，不能再挂 tile 同步对象，否则 AIC 会等待不存在的逐 tile ACK。Arch92 在调用 GMM2 时切换编译期通知参数，并在专家末 slice 完成后发布 per-expert ready，包含本核没有 MMAD tile 的情况。参见 [GMM2 通知分流](./mega_moe_wave.h#L334)、[专家 ready 发布](./mega_moe_wave.h#L377)。

唯一 AIV 按专家顺序运行去重 Combine，事件 Arm/Drain 每次成对；去重关闭时保持原来的量化/非量化消费方式。参见 [Combine 消费与排空](./mega_moe_wave.h#L426)、[去重入口接入](./mega_moe_wave.h#L526)。

## 7. 公共 GMM 与 Arch92 Wave 的既有差异

共享 GMM1 的新 upstream layout 选择和循环结构保留，同时传递原 Arch92 的 BlockMmad context、真实权重类型、GM handoff 策略及对应的 GM 地址。Arch35 A8W4 仍传入新的 pipeline；Arch92 generic 路径不构造 W4 prologue。参见 [共享 GMM1 调用](../arch35_92/mega_moe.h#L587)、[共享 GMM1 生命周期](../arch35_92/mega_moe.h#L698)。

公共 GMM1 增加 UseGmHandoff 参数：AIC 写 GM 并发布通知，唯一 AIV 等待后从 GM 取回完整 tile 做激活。MoE 与共享地址绑定都必须同步改变。参见 [AIC GM 执行](../arch35_92/stage/mega_moe_gmm1_activation.h#L141)、[通用执行分支](../arch35_92/stage/mega_moe_gmm1_activation.h#L435)、[MoE 地址绑定](../arch35_92/stage/mega_moe_gmm1_activation.h#L757)。

共享 GMM2 的 A 类型跟随 SwiGLU 实际输出；Arch92 A4W4 不进入 Arch35 FP8激活+FP4权重的转换路径。参见 [共享 GMM2 分流](../arch35_92/mega_moe.h#L743)、[共享 GMM2 对象生命周期](../arch35_92/mega_moe.h#L776)。

GMM2→Combine 的硬同步目标从固定 AIV1 偏移改为 (每 C 的 V 数−1)×16，Combine 分核也使用同一配比。参见 [目标事件偏移](../arch35_92/common/mega_moe_gmm_epilogue_sync.h#L296)、[Combine 分核](../arch35_92/stage/mega_moe_gmm2_combine.h#L366)。

Arch92 wave 仍保留以下专属编排，并未被 Arch35 的双 AIV wave 替换：

## 9. 验证与待跑项

## 10. Kernel 侵入式修改逐项检视清单

### 10.1 范围、基线与覆盖索引

### 10.12 非侵入项边界与跨文件复核

已确认 Arch35 的 `mega_moe_apt.cpp`、`mega_moe_layered.h`、三个 wave 文件只改公共头文件引用，不把它们列为函数体侵入式修改。R100 搬迁文件也不计入；尤其 `mega_moe_gmm_common.h`、BlockMmad/Prologue 实现和 epilogue/激活实现与本次基线一致。持久 context 的公共能力并不是这次新改的；**本次侵入的是基类共享调用增加 context 透传**，Arch92 新 wave 的 context 存储/类型复用属于独立新增代码。

以下为联动检视，不能用某个文件的单项通过代替：

- [ ] **编号链：** D01 → R10/R05 → R45/R47/R55 → R52，区分全 AIV 任务数与逻辑 C/V 对数；Arch35 保持 2N/N 原语义，Arch92 全部为真实 N。

- [ ] **FP4 链：** R06/R08 → R21/R23 → R34/R37 → R43/R48；量化输出类型、packed 存储、GM 地址和 GMM2 输入同时匹配，共享与 MoE 分别核对。
- [ ] **输入/count 链：** R18/R19/R26～R29 → R57/R59/R64；每个实际核只发布/消费应有事件，单 AIV 兼任任务不漏通知、不重复 read-done、不提前清表。
