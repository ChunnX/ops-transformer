代码确认

  • Dispatch 完成 MTE3 后，按该核覆盖的 expert-local 行数累加对应 256 行 wave flag。
  • AIC 每个 M-wave 首次任务轮询该 flag；256 行目标未满足不会消费。
  • GMM1 一个逻辑 tile 连续计算 gate、up 两次 MMAD，再通知 AIV0。
  • 只有一组 GMM1 Cube↔Vector flag；下一次本核 GMM1 在前一次 SwiGLU ack 之前不能下发。

目标 shape 推导

  • M=256、outputN=2N/2=2048，scheduler 有 1×8=8 个逻辑 tile/expert。
  • 每个逻辑 tile 内有 gate/up 两次 256-wide MMAD，所以是 16 次物理 MMAD/expert，但只占 8 个 scheduler owner。
  • 单专家只用约 8/36 核；不过 startBlockIdx += 8 且专家间无 barrier，使相邻专家能滚动填充不同物理核。

5. 为什么这种“看起来没那么激进”的主线可能是 460 μs

① GMM2 输出不做 GM round-trip

no-quant 主线把每个 128×256 tile 留在双槽 UB，AIV0 直接向目标窗口发 256 列片。没有“整行写本地 GM → 另一 AIV 再读整行”。

balanced 目标 shape 每 die 约 4096 路由行，bf16 H=4096 的完整输出约 32 MiB；GM 重建路径若完整写一次再读一次，会额外引入约 64 MiB 本地 GM 流量。该数值是 shape 推导。

② 没有 36→36 ready fan-in

主线 no-quant 不需要每个 AIC 发布 GM-ready，也不需要每个 AIV1 做 GM→UB、reduce/sum、V→S 轮询。GMM2 tile 只和配对 AIV0 通过硬件 cross-core flag 握手。

这与“实验分支 AIV Scalar 明显增大”的现象方向一致，但 20 μs 归因比例仍需同一版本 trace 才能量化。

③ Combine 从第一块 GMM2 tile 就开始

无需等完整专家或完整 wave。两槽允许 AIC 在 AIV0 发送前一 tile 时推进后一 tile，完成粒度是 128 token × 256 列，而非 expert/wave。

④ Dispatch 与 Combine 不争 AIV1

Phase 2 的 AIV1 专职 prefetch 下一专家；Phase 3 的 Combine 在 AIV0。主线没有“Combine 延迟下一 wave Dispatch，继而让 AIC 等输入”的同核资源冲突。

⑤ 简单滚动排核缓解 GMM1 低占用

单专家虽只有 8 个逻辑 owner，但 startBlockIdx 每专家前移 8，且无专家间 barrier。不同核可处于不同专家，16 个专家提供足够长的滚动任务流。

不能仅凭源码宣称的部分

HTML 证明拓扑与额外流量，不证明某块实际持续多少 cycle。460 μs 是否来自当前 090dfac1e、GMM1 单槽造成多少损失、GM round-trip 占多少，必须用相同二进制与 shape 的实测 trace 核对。
