# mega_moe 性能优化 — 62 用例全量验证（master vs megamoe-optimize）

> **环境**：A3（ascend910_93）/ arch22，单节点 16 卡，20 AIC + 40 AIV
> **基线**：`master` @ `0b0856d56` ｜ **优化分支**：`megamoe-optimize` @ `58c0bdf64`（6 个性能优化 + 1 个正确性修复）
> **覆盖**：BF16 非量化 + W8A8 量化，62 个用例（真实模型 shape + 边界 + 功能验证）

---

## 1. 总览

- **62/62 用例精度全 PASS**（`cos > 0.99` 且 `expert_token_nums` 严格相等）。性能上 **20 个用例提升 >1%、29 个持平、13 个小幅劣化（-1~-8%）**，平均 **+1.2%**。
- decode 场景（token ≤ 64）是 **HBM 权重搬运带宽受限**：权重搬运占耗时 >90%，算力利用率仅 12~28%。本分支的优化削减的是**固定串行开销**（与权重量无关的常数项），小模型场景提升 2~10%。
- dispatch/combine 并行化：rank 数远小于 48 个 AIV 核时，把单 rank 串行拉取改成 rank×token 二维并行，小 world_size 场景最高 **+30%**（boundary_maxdims_ws4）。
- 全部收益来自 **6 个经实测验证的优化 commit + 1 个正确性修复**，无行为重构、无精度牺牲。
- 少量劣化集中在 **token=512+ 的大 batch 且 rank 数 < 40 的分块场景**（-1~-8%，如 qwen2_57b_ws8）：该场景单 rank 搬运量已能喂满 MTE2，分块引入的调度开销超过并行收益；同场景另有大幅收益（boundary_maxdims_ws4 +29.7%、glm45_ws16 +7.9%），取舍以整体为准。

## 3. 六个优化方案的思想

全部为**只削减开销、不改变计算语义**的改动，每个都经全量回归验证。

### 3.1 开启硬件 unit flag（fixpipe ∥ Mmad 流水并行）

GMM 计算中 fixpipe（结果搬运）与 Mmad（矩阵乘）存在天然的流水机会，但默认关闭。
开启 `enableUnitFlag` 后硬件自动让两者重叠，`aic_fixpipe_ratio` 提升 5~10 倍，decode 场景 +0.2~1.2%。

### 3.2 编译期关闭 ExceptionDump 阶段插桩

kernel 内 11 处阶段打点恒开：每次执行取系统时钟 + 2 次 GM 写 + cache 刷写，且落在 HCCL 对称窗口内更贵。
编译期短路为零指令后，**固定开销 81.8 → 74.0us（−9.5%）**，有效带宽 1164 → 1308 GB/s。

### 3.3 CUMSUM 前缀和倍增化

路由统计的专家前缀和原为 O(EP) 串行依赖链（EP=16 时 15 次"小 Add + 全流水排空"）。
改为 Hillis-Steele 倍增扫描后依赖链降为 O(log₂EP)，**PipeBarrier 15 → 4**，该段耗时 4.81 → 0.80us。

### 3.4 ExpertTokenCount 按专家区间分核

路由后每个专家收到的 token 数原由**单核**统计（其余 36 核在栅栏干等，dec64 下 11.34us）。
按专家区间分摊到全部 sort 核：各核切片互不重叠、无需归约，**dec64 −9.4us**。

### 3.5 dispatch/combine rank×token 二维并行化

dispatch/combine 原为"每个 rank 一个 AIV 串行拉取"，而芯片有 48 个 AIV——rank 数少时大部分核闲置。
任务空间从 EP 扩展为 EP × tokenBlocks：按 token 数进一步分块，让空闲核参与搬运。
小 world_size 场景实测：boundary_maxdims_ws4 **+29.8%**、qwen3_235b_ws8 +5.3%、glm45_ws16 +7.2%。

### 3.6 自适应分块 + 碎片守卫

分块过细会把大 burst 切成碎片（8 行/块导致 kimi_k2_ws16 +26% 回归）。
按 `EP vs 核数`、`每 rank 块数`、`块大小下限` 三个判据动态决定是否分块及分块粒度，
回归消除（kimi_k2_ws16 ≈0，恢复小 rank 场景全部收益）。

### 3.7 正确性修复：分块按每 rank 实际行数（非平均）计算

分块任务数最初按"专家组的平均行数"估计，稀疏路由下部分 rank 的实际行数远超平均，
超出平均的行没有对应任务块而被丢弃（4 个 decode 用例精度 FAIL，cos 0.82~0.98）。
修复为按**每个 rank 的实际行数**（cumsum 前缀和相邻差）计算块数、任务空间压成连续序列，
每个 rank 的全部行恰好被一个块覆盖一次。修复后 4 个 FAIL 用例全部 PASS（cos=1.0），
性能收益不受影响（boundary_maxdims_ws4 修复后 +29.8%）。

## 4. 如何验证

### 4.1 编译与安装（两个分支各装一个 vendor 目录）

```bash
cd ops-transformer
source <CANN>/ascend-toolkit/set_env.sh
bash build.sh --pkg --soc=ascend910_93 --ops=mega_moe -j$(($(nproc)+1))
# 产物须约 20MB；22KB 说明 --soc 写错（必须小写）导致空包
ls -la build_out/cann-ops-transformer-custom_linux-aarch64.run
yes | ./build_out/cann-ops-transformer-custom_linux-aarch64.run --install-path=<VENDOR_DIR>
```

### 4.2 运行环境

```bash
source <CANN>/ascend-toolkit/set_env.sh
source <VENDOR_DIR>/vendors/custom_transformer/bin/set_env.bash
export MAX_JOBS=8 TORCH_EXTENSIONS_DIR=<独立目录>/.torch_extensions
```

### 4.3 精度 + 性能验证（单脚本合一，无需单独性能工具）

`golden_megamoe.py` 是**单脚本**（无外部依赖）：rank0 自动 profiler 抓取每个用例的 kernel Duration，
同时与 NPU 小算子级联参考（脚本内 `npu_mega_moe_golden`）比对精度——**一次跑出性能 + 精度**。

```bash
python3 golden_megamoe.py --list                     # 列出全部 62 个用例
python3 golden_megamoe.py --case dsv3_ws16_t32      # 单用例（输出 PASS + Dur）
python3 golden_megamoe.py --all                      # 全量（62 用例，约 45 分钟）
```

- **通过标准**：每 rank `cos > 0.99` 且 `etn_ok=True`（expert_token_nums 严格相等），总结输出 `62/62 通过`。
- 全量回归脚本：`scripts/run_regression.sh <vendor>`；5 用例快速抽样：`scripts/smoke5.sh <vendor>`。

## 5. 已否决方案备案（避免重复投入）

本轮共实测 10+ 个方案，以下均**已验证否决**，不建议重复尝试：

| 方案 | 实测结果 | 结论 |
|---|---|---|
| L2 预取（去掉 `CACHE_MODE_DISABLE`） | **+9.2% 劣化** | decode 下权重纯流式读、零复用，预取只冲刷 L2 |
| 缓存 HCCL window 基址 | **+10.9% 劣化** | `HcclShmem` 被 combine epilogue 热路径大量拷贝 |
| unpermute 全 AIV 化 | **+3~14% 劣化** | 省 2us 却新增全核 SyncAll（1.15us/次）栅栏 |
| 末轮 skew 整平（GMM2 动态窃取） | 名义 79us → 真实 7.7us | skew ≠ 可回收；最佳手段**会死锁**，split-N +32.4% |
| B 矩阵 stride padding | dsv3 可 −39us | 需改外部显存布局（+7% 显存），算子在内部做净亏 10 倍，已归档待调用方支持 |
| 提前发 flag0 / SyncAll 合并 | 天花板 2.4~7.2us | 位置决定成本：流水内几乎免费、头部满价；dispatch 栅栏结构上不可删 |
| 移除 GMM1 每专家 PipeBarrier | 噪声内 | MTE2 已饱和，气泡被排队请求自动填满 |
