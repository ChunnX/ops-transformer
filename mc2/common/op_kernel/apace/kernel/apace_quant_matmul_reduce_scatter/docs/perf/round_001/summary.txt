## 瓶颈分析

### 主 bound: CUBE BOUND

判定依据（以 basic_rank2 为例）：
- CUBE (aic_mac_ratio) 占 aicore_time = 96.0% > 80% → CUBE BOUND
- MTE2 (aic_mte2_ratio) 占 aicore_time = 73.5%（与 CUBE 流水并行，非独立 bound）
- AIV 侧 VEC 仅 4.6%、MTE2 仅 5.6% → 通信+reduceSum 开销小

### 关键发现

1. **wall-clock perf 模式不可用**：main.cpp perf 模式测量 `<<<>>>` 异步启动开销（0.003-0.010 ms），
   不反映真实 kernel 执行时间。实际 Task Duration 为 0.945-2.374 ms（msprof device-side）。
   **性能评估必须以 msprof Task Duration 为准。**

2. **AIC CUBE 利用率高（96%）**：matmul 计算充分占满 cube 流水，AIC 侧无明显气泡。

3. **AIV 侧大量空闲**：aiv_time ≈ Task Duration（MIX_AIC_1_1 同块共存），
   但 aiv_vec_time 仅 ~50 us（4.6%），说明 AIV 大部分时间在等待 AIC 完成 + 跨 rank 同步。
   AllToAll 通信 + reduceSum 实际执行时间 < 120 us，远小于 matmul 的 ~1060 us。

4. **rank 数对性能影响有限**：basic_rank2 (1.110ms) vs basic_rank4 (0.945ms)，
   4 rank 反而更快——因为 4 rank 时 chunkM=512（更小的通信量），且 4 张卡并行 matmul。

5. **大 M 场景线性扩展**：largeM_rank2 (M=4096) = 2.374ms ≈ 2× basic_rank2 (1.110ms)，
   符合 matmul O(M) 线性扩展预期。

6. **大 K 场景**：largeK_rank4 (K=8192) = 1.096ms，与 basic_rank4 (K=3584) = 0.945ms 相比，
   K 翻倍仅增 16%，说明 stepK=2 的 K 循环效率高。

### 优化建议（后续 round 可探索）

- 当前 CUBE 利用率已达 96%，AIC 侧优化空间有限
- AIV 通信侧有大量空闲，可探索 local 前置（matmul 完成一部分即启动通信）以重叠计算与通信
- 可探索多 tile 通信（当前单 tile，chunkM 一次传完）以减少通信气泡
- cube_utilization(%) 仅 ~7.5%，28 核中可能有负载不均，可探索 block swat 优化
