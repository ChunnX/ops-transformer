### 性能未提升的根因分析

多 tile PUT 优化未带来性能提升，根因如下：

1. **AIC matmul 与 AIV 通信仍然串行**：AIC 一次性算完整个 C_i 后才通知 AIV 开始通信。
   多 tile 只改变了 AIV 侧的通信+reduceSum 分块方式，没有实现 AIC matmul 与 AIV 通信的重叠。
   
2. **local 前置不可行**：要实现 AIC 按 tile 分批通知 AIV（AIC tile N matmul || AIV tile N-1 comm），
   需要修改 QuantMatmulMxKernel 的 BlockScheduler 循环（apace 共享层，禁止修改）。
   
3. **reduceSum 开销占比小**：AIV VEC+MTE2 仅 ~115us（占 Task Duration ~5%），优化空间有限。
   AIC CUBE matmul ~1060-2335us（占 ~96%），是绝对主导。

4. **多 tile 通信的额外开销**：多 tile 导致 SyncAll 次数增加（tileCnt 次 vs 1 次），
   SyncAll 的同步开销可能抵消了 reduceSum 分块的收益。

### 后续优化方向（需要架构变更）

1. **local 前置（需 Architect 评估）**：修改 QuantMatmulMxKernel 或在外部 wrapper 中按 tile 分批调用 matmul，
   实现 AIC tile N matmul || AIV tile N-1 comm 的真正流水重叠。
   
2. **多 block 通信（需 Architect 评估）**：teamBarrier totalJobs=rankSize，让前 rankSize 个 block 并行通信，
   减少 block 0 的通信串行瓶颈。

3. **GET 模式评估**：GET 模式的 AIV 拉取可能比 PUT 推送更高效（取决于硬件 URMA 引擎），
   但需要额外拷贝开销。需要 Architect 评估 GET 钩子的稳定性和性能。

## 优化内容

### 已实施优化
1. **多 tile 通信（PUT 模式）**: commTilingData 从单 tile 改为多 tile（headMSize=512）
   - basic_rank2: tileCnt=2（chunkM=1024, headMSize=512）
   - basic_rank4: tileCnt=1（chunkM=512, headMSize=512）
   - largeM_rank2: tileCnt=4（chunkM=2048, headMSize=512）
   - largeK_rank4: tileCnt=1（chunkM=512, headMSize=512）
2. **reduceSum 多 tile 分块**: reduce_sum.h 添加 RunTile 方法，按 tile 分块处理
   - 地址偏移用 totalChunkM（跨 rank 步进），处理大小用 tileM
   - 每 tile 独立 float32 累加，精度无损

### 未实施优化（设计问题）
1. **GET 模式**: 评估后未切换
   - 原因: GET 多 tile 需要 AIV 额外拷贝 workspace→win 区（数据搬运量 2x PUT）
   - GET 钩子官网无算子样例（仅契约级描述），风险高
   - PUT 多 tile 无需额外拷贝，且 DESIGN.md 允许 "PUT 或 GET"
2. **local 前置**: 不可行
   - 原因: 需要修改 QuantMatmulMxKernel（apace 共享层，禁止修改）
   - AIC matmul 按 tile 分批通知 AIV 需要侵入 BlockScheduler 循环
