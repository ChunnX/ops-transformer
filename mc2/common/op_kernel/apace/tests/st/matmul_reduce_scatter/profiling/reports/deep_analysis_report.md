## 6. 关键发现

- **通信Bound**（68 用例）: vs 级联中位加速比 **1.23x**, vs 融合中位 **1.16x**
- **均衡**（28 用例）: vs 级联中位加速比 **1.26x**, vs 融合中位 **1.07x**
- **计算Bound**（1 用例）: vs 级联中位加速比 **1.04x**, vs 融合中位 **1.05x**

### 核心洞察

1. **70% 用例为通信 Bound**（R < 0.67），级联基线中通信耗时远超计算耗时。
   这解释了 apace ST 融合方案的整体优势 —— 通信 Bound 场景下流水掩盖收益最大。

2. **rank4 vs 融合算子加速比（中位 1.32x）高于 rank2（1.13x）**
   rank4 时级联基线的通信开销更大（3 个远端 vs 1 个），融合掩盖收益更显著。

3. **K > 4608 时 vs 融合算子优势收窄至 1.07x**（中位），K ≤ 1024 时仅 1.15x：
   - 大 K 场景 matmul 占比高，apace kernel 的 matmul 效率与库算子差距成为瓶颈
   - 小 K 场景通信固定开销占比高，融合收益被稀释

4. **N ≤ 1024（极窄 N）时 vs 级联中位降至 0.83x**：
   小消息 URMA PUT 固定开销占比过高，HCCL 对小消息优化更好，属架构性 trade-off

### 后续优化方向

1. **大 K matmul 效率**（K > 4608, ~10% 差距）: 调优 baseK/stepK/scaleKL1 tiling 参数
2. **小 N 通信效率**（N ≤ 1024）: 评估 URMA PUT batching 或改用小消息优化的通信模式
3. **rank2 场景融合算子对比**（vs 融合仅 1.13x）: rank2 时通信掩盖空间有限，重点提升 matmul 本身
